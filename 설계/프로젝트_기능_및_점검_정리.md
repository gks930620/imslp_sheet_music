> 작성일: 2026-07-06
> 대상: `spring_csr_boiler_react` (Spring Boot 백엔드 + React(Vite) 프론트, 단일 서버 통합 배포 보일러플레이트)
> 목적: (1) 프로젝트에 어떤 기능이 있는지 정리, (2) 설계 원칙 부합 여부 점검, (3) 문서 오류 및 문서-코드 불일치 점검

## 1. 프로젝트 한눈에

- **형태**: CSR 보일러플레이트. Spring Boot가 REST API를 제공하고, React SPA가 화면을 담당. 최종적으로 React 빌드 산출물을 Spring `static`에 포함해 `http://localhost:8080` **단일 서버**로 동작.
- **기술 스택**
  - 백엔드: Spring Boot 3.3.4 / Java 17 / Spring Web · Security · Validation · WebSocket · OAuth2 Client · Data JPA · Data JDBC · Actuator
  - 쿼리: QueryDSL 5.0.0 (jakarta)
  - 인증: JWT (JJWT 0.12.3), OAuth2 (카카오/구글), HttpOnly 쿠키 방식
  - DB: **개발/테스트 = 인메모리 H2(MySQL 호환), 배포 = Railway MySQL**(prod 프로파일, `mysql-connector-j`, MySQLDialect)
  - 파일 저장: 로컬 파일시스템 / Supabase Storage (Strategy 패턴 전환)
  - 프론트: React + Vite, react-router-dom, @stomp/stompjs + SockJS, DOMPurify
  - 문서화/모니터링: springdoc-openapi(Swagger UI), Actuator health
  - 환경변수: `me.paulschwarz:spring-dotenv` (`.env` 로딩)
  - 배포: Dockerfile (멀티스테이지)

## 3. REST API 엔드포인트 정리

### 인증/사용자
| 메서드 | 경로 | 권한 | 처리 |
|--------|------|------|------|
| POST | `/api/login` | permitAll | `JwtLoginFilter` (JSON: username/password) |
| POST | `/api/logout` | authenticated | `CustomLogoutSuccessHandler` |
| POST | `/api/users` | permitAll | 회원가입 `JoinController` |
| GET | `/api/users/me` | authenticated | 내 정보 `UserController` |
| POST | `/api/tokens/refresh` | permitAll | 토큰 재발급 `RefreshController` |
| GET | `/custom-oauth2/login/web/{provider}` | permitAll | 웹 OAuth2 시작 |
| POST | `/api/oauth2/providers/{provider}/tokens` | permitAll | 앱 OAuth2 토큰 교환 |

### 게시판/댓글
| 메서드 | 경로 | 권한 |
|--------|------|------|
| GET | `/api/communities` | permitAll (목록/검색·페이징) |
| GET | `/api/communities/{communityId}` | permitAll (상세) |
| POST | `/api/communities` | authenticated |
| PUT | `/api/communities/{communityId}` | authenticated |
| DELETE | `/api/communities/{communityId}` | authenticated (소프트삭제) |
| GET | `/api/communities/{communityId}/comments` | permitAll |
| POST | `/api/communities/{communityId}/comments` | authenticated |
| PUT | `/api/comments/{commentId}` | authenticated |
| DELETE | `/api/comments/{commentId}` | authenticated |

### 파일
| 메서드 | 경로 | 권한 |
|--------|------|------|
| GET | `/images/{filename}` | permitAll (로컬 이미지 서빙) |
| GET | `/api/files/paths` | permitAll |
| GET | `/api/files` | **permitAll** (공개 조회 API로 정합화 완료) |
| GET | `/api/files/{fileId}/content` | permitAll (다운로드) |
| POST | `/api/files` | authenticated (업로드) |

### 채팅
| 유형 | 경로 | 권한 |
|------|------|------|
| GET | `/api/rooms` | authenticated |
| GET | `/api/rooms/{roomId}` | authenticated |
| POST | `/api/rooms` | authenticated |
| STOMP pub | `/pub/room/{roomId}` | CONNECT 시 JWT 인증 |
| STOMP sub | `/sub/room/{roomId}` | 구독 |

## 4. 도메인(엔티티) 정리

| 엔티티 | 테이블 | 주요 필드 | 연관관계 |
|--------|--------|-----------|----------|
| `UserEntity` | `users` | id, provider, username(unique), password, email, nickname, isActive, roles(List\<String\>), createdAt, updatedAt | 없음 |
| `RefreshEntity` | (기본) | id, userEntity(@ManyToOne LAZY), token(unique) | User(N:1) |
| `CommunityEntity` | `community` | id, user(@ManyToOne), title(≤200), content(TEXT), viewCount, isDeleted, createdAt, updatedAt | User(N:1) / 편의메서드: incrementViewCount, update, softDelete, isWrittenBy |
| `CommentEntity` | `comment` | id, community(@ManyToOne), user(@ManyToOne), content(TEXT), isDeleted, createdAt, updatedAt | Community(N:1), User(N:1) |
| `FileEntity` | `files` | id, originalFileName, storedFileName, filePath, fileSize, contentType, refId, refType(enum: COMMUNITY/USER), fileUsage(enum: THUMBNAIL/IMAGES/ATTACHMENT), createdAt, updatedAt | 없음(참조는 refId+refType) |
| `RoomEntity` | `chat_room` | id, name | 없음 |

- **양방향 연관관계 없음** → 설계 원칙("양방향 지양, 단방향 @ManyToOne") 준수.
- 파일은 FK 대신 `refId + refType`로 느슨하게 연결 (게시판/사용자 재사용 가능).

## 6. 설계 원칙 부합 점검 (핵심)

| 원칙 | 판정 | 근거/예외 |
|------|------|-----------|
| Controller→Service→Repository, Controller에서 Entity/Repository 금지 | **대체로 준수(개선됨)** | Community/Comment/Room 준수. `AppOAuth2Controller`는 `AppOAuth2Service`로 분리 완료. 잔여: `FileController`가 `FileEntity.RefType/Usage`(enum이 엔티티에 중첩) 및 다운로드에서 `FileEntity` 사용 — enum 분리 리팩터링은 향후 과제. |
| 1 API = 1 Controller = 1 Service | **부분 준수** | CRUD는 준수. `AppOAuth2Controller`는 서비스로 이관됨. `RefreshController`는 여전히 인라인 오케스트레이션, `UserController.getMyInfo`는 principal로 Map 구성(서비스 없음). |
| DTO 변환 `dto.toEntity()` / `DTO.from(entity)` | **대체로 준수** | 대부분 구현됨. `JoinDTO`만 `toEntity()` 없음(서비스에서 setter로 생성). `FileService.saveFiles`는 빌더로 직접 생성. |
| 표준 응답/에러 코드 (400/403/404/409) | **준수(개선됨)** | 예외→상태 매핑 정확. `FileController` JSON 엔드포인트를 전역 핸들러 위임으로 표준화 완료. 바이너리 서빙(다운로드/이미지)만 관례적 `notFound().build()` 유지. |
| JWT HttpOnly 쿠키, Access 30분·Refresh 4시간+DB, 회전, secure 환경분기 | **준수** | 쿠키명 `access_token`/`refresh_token`, `httpOnly(true)`, `secure(${app.cookie.secure})`. 만료 access 1,800,000ms(30분)·refresh 14,400,000ms(4시간) — dev/prod/test 모두 일치. Refresh DB 저장 + 회전(기존 삭제 후 신규 발급). |
| SecurityConfig 경로 권한 | **준수** | 문서의 permitAll/authenticated 규칙과 일치. `.anyRequest().authenticated()`로 끝나는 **화이트리스트(기본 차단)** 방식. 파일 GET 계열(`/api/files`, `/api/files/paths`, `/api/files/*/content`)은 의도적으로 permitAll. |
| 파일: 별도 API + enum 구분 + Strategy(supabase.enabled) | **준수** | `/api/files` 분리, `RefType`/`Usage` enum, `@ConditionalOnProperty`로 Local/Supabase 빈 전환. |
| STOMP: SockJS + 핸드셰이크/채널 JWT, 메시지 DB 미저장, pub/sub | **준수** | `/ws-chat`+SockJS, `HttpHandshakeInterceptor`(쿠키→세션 username), `JwtChannelInterceptor`(CONNECT 인증), `ChatController`는 `convertAndSend`만(미저장). |
| JPA 단방향, 환경 분리 | **준수** | `@OneToMany` 없음(모두 단방향 `@ManyToOne`). dev create / prod update. |

## 7. 발견된 문제 · 문서 오류 · 문서-코드 불일치 (+ 조치 결과)

> 아래 항목 중 코드/설정으로 조치한 것은 ✅ 수정완료, 판단상 남겨둔 것은 🟡 유지(사유 명시)로 표시.
> Java main/test 컴파일 성공 확인. (통합 테스트는 로컬 MariaDB:3406 미기동으로 실행 보류 — 기존 테스트는 해피패스만 검증하여 변경과 충돌 없음)

### 🐞 코드 버그
1. ✅ **`RoomService.getRoom` 500 → 404.** `RuntimeException` → `EntityNotFoundException.of("채팅방", roomId)`로 변경. (`RoomService.java`)
2. ✅ **`RoomService.createRoom` 중복 400 → 409.** `IllegalArgumentException` → `DuplicateResourceException`, 빈 이름은 `BusinessRuleException`(400)로 변경.
3. ✅ **`FileController` 응답 표준화.** JSON 엔드포인트(paths/upload/detail/delete)의 try/catch·`.build()` 제거 → 예외를 `GlobalExceptionHandler`에 위임해 `ErrorResponse` 일관 반환. (다운로드/이미지 서빙은 바이너리라 기존 방식 유지)
4. ✅ **`FileService.deleteFile` 물리 파일까지 삭제.** `FileUtil.deleteFile` 위임 추가, not-found는 `EntityNotFoundException`(404). 아울러 `LocalFileStorage.deleteFile`이 웹 경로(`/uploads/xxx`)를 실제 업로드 디렉토리 기준으로 해석하도록 수정(기존엔 절대경로로 오인해 삭제 실패).
5. 🟡 **`UserEntity.roles` — 유지(주석으로 문서화).** 확인 결과 Hibernate 기본 직렬화로 `users.roles`(BLOB) 컬럼에 저장되어 **정상 동작**(seed도 직렬화 blob 사용). `@ElementCollection` 전환은 `data-users.sql`(111행) + prod 스키마 마이그레이션이 수반되고, 현재 `roles`는 인가(`hasRole`)에 사용되지 않아 리스크 대비 실익이 없어 보류. 엔티티에 전환 가이드 주석 추가.

### 🔐 설계 레벨 이슈
6. ✅ **`AppOAuth2Controller` 레이어 분리.** Repository/Entity/토큰 발급 로직을 신규 `AppOAuth2Service`로 이관, 컨트롤러는 서비스 호출 + 표준 응답만 담당. 검증 실패는 `BusinessRuleException`(400).
7. ✅ **`SecurityConfig` 화이트리스트(기본 차단) 적용 완료.** `.anyRequest().authenticated()` 로 끝나 명시되지 않은 엔드포인트는 인증을 요구한다. 공개 SPA에 필요한 정적 번들(`/assets/**`)·favicon·OAuth 콜백·공개 조회 API는 상단 permitAll 목록에 명시했고, 민감 쓰기/사용자 엔드포인트는 명시적 `authenticated()` 로 보호된다. **새 공개 경로 추가 시 permitAll 목록에 등록**하는 것이 유일한 유지 규칙.

### 📄 문서-코드 불일치 / 문서 오류
8. ✅ **`KAKAO_CLIENT_SECRET` 보완.** `.env`에 키 추가(빈 값 허용 안내), `application.yml`은 `${KAKAO_CLIENT_SECRET:}` 빈 기본값으로 기동 실패 방지.
9. ✅ **파일 GET 권한 문서 정합화.** `설계/csr_프로젝트_구조_정리.md`의 SecurityConfig 경로표를 실제(파일 GET=permitAll, POST/DELETE만 authenticated)와 일치하도록 수정.
10. ✅ **RefType/Usage 표현 정정.** 설계 문서에 `RefType`(참조 대상: COMMUNITY/USER)과 `Usage`(용도: THUMBNAIL/IMAGES/ATTACHMENT) 구분을 명확히 기재.
11. ✅ **`Dockerfile` 프론트 빌드 포함.** builder 스테이지에 Node 20 설치 + `COPY frontend` 추가 → `bootJar` 시 `processResources`가 React 번들을 static으로 포함. `.dockerignore`에 `frontend/node_modules`·`dist` 제외 추가.
12. 🟡 **`data-init.sql` 미참조 — 유지.** 어떤 `data-locations`에도 없는 잔재이나, 수동 초기화용 스크립트로 남을 수 있어 삭제하지 않고 보류(삭제 원하면 제거 가능).
13. ✅ **파일 저장 = 로컬(운영 포함), Supabase 미사용.** 배포 방침 확정에 따라 prod도 `supabase.enabled=false`로 로컬(컨테이너) 저장 사용. `SUPABASE_*` 환경변수 불필요(빈 기본값). 코드에는 Supabase 전략이 남아있어 필요 시 재전환 가능. ⚠️ Railway 파일시스템은 ephemeral → 영속화 시 Volume 을 `/app/uploads` 에 마운트.

### ✅ 문서가 코드와 정확히 일치하는 항목 (검증됨)

## 8. 프론트엔드 정리 항목 (원칙 위반 아님, 개선 후보)
- `uploadFiles`(FormData → `/api/files`) 헬퍼가 `CommunityWritePage`/`CommunityEditPage`에 동일 중복 → `lib/http.js`로 승격 권장.
- `authFetch(...) + if(!res.ok) throw await toApiError(res)` 패턴이 3곳 반복 → 공통 헬퍼로 정리 권장.
- `AuthContext`의 login/logout이 `callPublicApi` 대신 raw `fetch` 사용(동작엔 문제없음, 일관성만 소폭 저하).
- 댓글 수정 UX가 `window.prompt` 기반(`CommunityDetailPage.jsx:98`) → 추후 공통 UI 컴포넌트화 권장.
- 게시글 본문은 `dangerouslySetInnerHTML` + DOMPurify 정화 사용(안전 처리됨).
