## 1. HTML 파싱 — jsoup 도입

**결정**: `implementation 'org.jsoup:jsoup:1.21.1'` (MIT, 의존성 없음).

**근거**: 작품 페이지가 0.4~1MB·수만 태그이고 라벨이 `span.mh555/ms555` 로 쪼개져 있어(00 조사 §1-2) 정규식 파싱은 깨진다. 필요한 것은 CSS 셀렉터, `attr()` 의 엔티티 자동 디코딩(`data-id` 가 `https&#58;//…`), 관대한 파서 — 전부 jsoup 기본. JS 실행은 불필요함을 확인했으므로(정적 HTML 에 파일 목록 전부 존재) HtmlUnit/Selenium 은 과하다.

**위키텍스트**(`api.php prop=wikitext`)는 `|키=값` 줄 단위라 라이브러리 없이 `ImslpWikitextParser` 로 직접 파싱한다. 작품 1건당 **HTML 1회 + 위키텍스트 1회**(00 §3-3 권고) — HTML 에서 파일ID·크기·쪽수·다운로드수·섹션·한국어 제목, 위키텍스트에서 편집자·출판사·저작권·편성·조성·연도를 얻고 `imslp_original_file_name` 으로 조인한다.

**버린 대안**: 정규식 단독(취약) / HtmlUnit(무거움, 불필요) / HTML 단독(가능하지만 판본 필드 정리 비용이 큼).

## 2. PDF 쪽수·첫 페이지 미리보기 — Apache PDFBox, 기존 저장 전략 재사용

**결정**
- `implementation 'org.apache.pdfbox:pdfbox:3.0.5'` (Apache-2.0).
- 쪽수: `Loader.loadPDF(new RandomAccessReadBufferedFile(tempFile))` → `getNumberOfPages()`. 전체를 메모리에 올리지 않는다(50MB 스캔 PDF 대비).
- 미리보기: `PDFRenderer.renderImageWithDPI(0, 72, ImageType.RGB)` → PNG. A4 기준 약 595×842px, 100~300KB. 폭이 800px 를 넘으면 800px 로 축소.
- 저장 위치: **PDF·PNG 모두 기존 `FileStorageStrategy`(로컬 디스크 ↔ Railway 버킷)** 에 저장하고 `files` 테이블 행으로 메타를 관리한다(01_ERD §3-6). 서빙은 기존 `GET /uploads/{key}` 프록시 — 별도 미리보기 API 없음.
- **`FileStorageStrategy` 확장**: `FileUploadResult store(String originalFilename, String contentType, Path source)` 를 추가한다(로컬·버킷 둘 다 구현). 기존 `uploadFile(MultipartFile)` 은 유지. 이유: 크롤러가 받은 PDF 와 PDFBox 가 만든 PNG 는 `MultipartFile` 이 아니다. 업로드는 항상 **임시 파일(`Files.createTempFile`) → 검증(매직바이트 `%PDF`, 크기) → PDFBox → 저장 전략 → 임시 파일 삭제** 순서로 흐른다(멀티파트도 `transferTo(temp)` 후 같은 경로).
- `files` 컬럼 의미: `ref_type=EDITION`, `file_usage=ATTACHMENT`(PDF) / `THUMBNAIL`(PNG), 업로드 직후 `ref_id=0`, 판본 저장 시 `ref_id=edition.id`(기존 `linkTo`). 기존 orphan 배치(24h)가 미연결 파일을 치운다.
- 미리보기 생성 실패(암호화·손상 PDF)는 삼키고 `previewFileId=null` 로 응답 — 업로드·수집을 막지 않는다(화면 "미리보기 준비 중").

**근거**: PDFBox 는 순수 자바, 렌더링·쪽수 둘 다 한 라이브러리. 별도 파일 테이블을 만들지 않는 이유는 저장 전략·서빙 프록시·orphan 정리·삭제 연동(컨벤션 §5-3-1)이 이미 `files` 기준으로 구현돼 있어 그대로 얻기 때문.

**버린 대안**: pdf.js(프론트 렌더 — 미리보기를 매번 클라이언트가 만들면 목록 화면에서 PDF 전체를 내려받게 됨) / Ghostscript(외부 바이너리, Railway 이미지에 없음) / `Usage` 에 `SCORE_PDF/PREVIEW` 추가(의미는 더 명확하나 공용 enum 변경 범위를 줄이기 위해 보류 — 필요해지면 그때).

## 3. 수집 잡 실행 구조

**결정**: Spring 앱 내부, **관리자가 개시하는 비동기 워커 1개**, 진행 상태는 전부 DB(`crawl_job`/`crawl_item`).

| 항목 | 결정 |
|---|---|
| 실행기 | `ThreadPoolTaskExecutor` 빈 `imslpExecutor` — **core=max=1, queue 무한**. 수집 작업과 단건 "파일 받아오기"(02 §5-7)가 **같은 스레드**를 쓴다 → IMSLP 커넥션은 항상 1개. `@Async("imslpExecutor")` 로 `CrawlWorker.run(jobId)` / `EditionFileFetcher.fetch(editionId)` 제출 |
| 상태 원본 | DB. 워커는 항목마다 `crawl_item`/`crawl_job` 을 갱신하고 화면은 10초 폴링(02 §6-6). 인메모리 상태 없음 → 브라우저를 닫아도, 서버가 죽었다 살아나도 현황이 남는다 |
| 동시 1작업 | `CrawlService.start/resume` 이 `status IN (RUNNING, PAUSED)` 존재 시 409. 인스턴스는 1개 전제(Railway 단일 서비스). 수평 확장 시 DB 락 도입 — 1차 범위 밖 |
| 중지 | `stop` 은 `stop_requested=true` 만 세팅. 워커가 항목 경계마다 확인해 처리 중 항목을 마친 뒤 `STOPPED`. PAUSED 상태의 stop 은 즉시 STOPPED |
| 재시작 복구 | `CrawlStartupRecovery(ApplicationRunner)`: RUNNING/PAUSED → `STOPPED, stopped_by_restart=true`, PROCESSING 항목 → `FAILED/INTERRUPTED`. 자동 재개하지 않는다(관리자가 "이어서 시작") |
| 재개 | `resume` → status RUNNING, 워커 재제출. PENDING 항목부터. 이미 `imslp_file_id` 로 파일이 붙은 판본은 건너뛴다("파일당 평생 1회") |
| 일시 정지 | IMSLP 무응답(타임아웃·5xx·429·봇 게이트 302 반복) **연속 3항목** → PAUSED, `paused_until=now+10분`. 워커는 스레드를 놓지 않고 5초 단위로 자며 `stop_requested`/`paused_until`/resume 을 확인한 뒤 계속. 2번째 PAUSED 도 3연속 실패면 STOPPED + 사유 |
| 요청 간격 | `ImslpGate.awaitRequestSlot()`: **최소 2초** 간격(robots `Crawl-delay: 2`). 상수 `app.imslp.request-interval-ms=2000`(테스트 0). ⚠️ 현재 구현은 `lastRequestAt` 을 요청 **시작 직전**에 찍는다 — 주석의 "직전 요청 **완료** 시각 기준"과 어긋난다. 페이지 요청(수백 ms)에선 차이가 없지만 **8MB 파일을 60초 걸려 받고 나면 다음 요청은 간격 0초로 나간다**(2026-09-07 실 IMSLP 사고의 배경). 주석은 코드에 맞춰 정정했다(시작 기준). 파일 경로에서는 대기 자리를 바로잡은 뒤 큰 문제가 아니다 — 파일 GET 앞에 15초가 있어 파일 호스트에 가해지는 페이스는 파일당 ≥15초다. 남는 구멍은 "큰 파일 수신 완료 직후 다음 곡의 대기 페이지 GET 이 간격 0으로 나가는 것" 하나이고, 이건 가벼운 페이지 요청이라 우선순위가 낮다 |
| **파일 대기(15초)** | `ImslpGate.awaitFileWait()` 를 **파일 1개마다 정확히 1회**, **`resolveFileUrl()`(대기 페이지 GET) 다음 · `downloadResolvedFile()`(파일 GET) 앞**에 부른다. 자리는 **`EditionFileFetcher.downloadAndStore`** — 수집 워커(곡당 최대 2개 루프)와 개별 받아오기(02 §5-7)가 모두 이 메서드를 지나므로 한쪽만 빠질 수 없고, 통합테스트가 이벤트 순서 `RESOLVE:{id}` → `FILE_WAIT` → `DOWNLOAD:{id}` 로 관찰한다(`ImslpFileWaitPolicyIntegrationTest`). 상수 `app.imslp.file-wait-ms=15000`(테스트 0) — 값 판단은 표 아래 「파일 대기 값(15초) 판단」 참고. **2026-09-07 재정정(2차)** — 1차 정정에서 대기를 `downloadFile()` **직전**(= 대기 페이지를 열기도 전)에 뒀는데, 그러면 15초를 다 쓴 뒤 카운트다운 페이지를 받고 **0.3초 만에** 파일을 치게 된다. 브라우저는 정반대(페이지 로드 → 카운트다운 → 파일)이고, 서버에는 정확히 "카운트다운을 안 기다린 클라이언트"로 보인다 — 기획 §9-1 "15초 대기를 우회하지 않고 그대로 기다린다" 위반. 그래서 `ImslpClient` 를 2단계로 쪼개 대기 자리를 두 호출 **사이**로 끌어냈다(한 메서드 안에 감추면 컨벤션 §6 의 컨트롤러 통합테스트로 관찰할 수 없다) |
| 파일 1건의 HTTP 요청 수 | 요청 **2회**이고, 이제 메서드도 2개다 — `resolveFileUrl(id)`: `GET Special:ImagefromIndex/{id}` → `span#sm_dl_wait[data-id]` 를 읽어 `ImslpFileLocation` 반환(**여기서 기다리지 않는다**). `downloadResolvedFile(location, dir)`: 그 1회용 주소로 파일 GET. 게이트 분담 — 대기 페이지 앞의 `awaitRequestSlot()` 은 **호출자**(`downloadAndStore`)가, 파일 GET 앞의 `awaitRequestSlot()` 은 **구현체**가 부른다(앞에 15초가 있어 실제 대기는 0이지만 `lastRequestAt` 을 파일 요청 시각으로 갱신한다). `ImslpFileLocation` 은 호스트가 요청마다 바뀌는 1회용 주소라 저장·재사용하지 않는다 |
| HTTP 클라이언트 | JDK `java.net.http.HttpClient` (새 의존성 없음). `followRedirects(NEVER)`(봇 게이트 302 판별), 타임아웃 connect 10s / read 60s(파일 300s), `Accept-Encoding: gzip` + 응답 `Content-Encoding` 확인 후 `GZIPInputStream` 수동 해제(00 §1 — 요청 안 해도 gzip 으로 옴), 파일은 스트리밍으로 임시 파일에 기록 |
| User-Agent | `app.imslp.user-agent` = `SheetMusicKR/0.1 (+https://{APP_BASE_URL}; contact: {APP_CONTACT_EMAIL})` — 연락처는 환경변수 `APP_CONTACT_EMAIL`(로컬 기본값 저장소 소유자 메일) |
| 쿠키 | `redirectPassed=1`(클라이언트 생성 쿠키) + `imslpdisclaimeraccepted=yes`(첫 파일에서 `IMSLPDisclaimerAccept/{id}` 1회 호출로 발급, 30일). `CookieManager` 대신 두 쿠키를 명시 헤더로 보낸다(00 §2-2 실측 흐름). 최종 URL 은 `span#sm_dl_wait[data-id]` 를 읽는다(호스트가 요청마다 바뀜) |
| 파일 검증 | `Content-Type: application/pdf`, `Content-Length` 일치, 매직바이트 `%PDF`. 어긋나면 `FILE_DOWNLOAD_FAILED`, 재시도 없음(관리자가 "파일 받아오기") |
| 파일 받기 스위치 | 작업 생성 요청의 `fetchFiles`(기본 true) → `crawl_job.fetch_files` 스냅샷. false 면 메타데이터만(=조사 B안). 워커 코드는 `if (job.isFetchFiles())` 분기 하나 |
| 어떤 파일을 받나 | `kind=COMPLETE_SCORE AND scope=COMPLETE AND imslp_license_code IN (PD, CC0, CC_BY, CC_BY_SA)` 중 `imslp_download_count` 상위 2개(01 §9-1). 피아노 독주가 아니면(위키텍스트 `Instrumentation` ≠ `piano` 이고 `api.php categories` 에 `For piano` 없음) 곡은 만들되 숨김, 파일은 받지 않음 |

#### 파일 대기 값(15초) 판단 — 2026-09-07

**결정: `app.imslp.file-wait-ms=15000` 을 유지한다.** 20000 으로 올리지 않는다.

- 간헐 실패의 원인 후보는 **값이 아니라 자리**였다. 이전 순서에서 "직전 파일 수신 완료 후 15~16초" 는 관찰된 사실이지만, 같은 순간 **대기 페이지를 받은 지는 0.3초**였다. IMSLP 가 보는 것은 후자다 — 카운트다운을 띄운 세션이 카운트다운을 무시하고 파일을 친 것. 이 상태에서 값만 20초로 올리면 대기 페이지→파일 간격은 여전히 0.3초라 아무것도 고쳐지지 않고, 곡당 +10초(100곡이면 +17분)만 손해다.
- 순서를 고치면 대기 페이지→파일 간격이 **실측 15초 이상**이 된다. 우리 카운트다운은 대기 페이지 응답을 *다 받고 파싱한 뒤* 시작하므로 브라우저(페이지 로드 시점 시작)보다 **늦게** 시작해 늦게 끝난다 — 이미 여유가 붙어 있다.
- 15초는 IMSLP 가 정한 수치이고 우리 약속은 "그대로 기다린다"(기획 §9-1)이지 "더 기다린다"가 아니다. 근거 없이 올리면 정책 준수가 아니라 처리량만 잃는다.
- **재평가 조건**: 순서 수정 후에도 파일 호스트 GET 이 302/429 로 튕기면(대기 페이지는 200) 그때 20000 을 **단일 변수로** 시험한다. 판단 근거는 backend-dev 가 보강한 로그 — 파일 호스트 응답의 상태·host·location·retry-after 가 남는다. 반대로 대기 페이지가 302 면 값 문제가 아니라 쿠키·UA·IP 제한 문제다.

> **2026-09-22 정정.** 바로 위 마지막 문장("대기 페이지가 302 면 값 문제가 아니라 쿠키·UA·IP 제한 문제다")은 **이제 전부 맞지 않는다.**
> 운영 로그 실측(00 §2-1 2026-09-22 보충)으로, 쿠키 2개를 정상 조합으로 보냈는데도 대기 페이지 GET(`Special:ImagefromIndex/{id}`)이
> 302 를 주는 경우가 있고, 그게 **쿠키·UA·IP 문제가 아니라 대기 페이지를 생략한 정상 파일 리다이렉트**인 사례가 확인됐다
> (`Location: https://s9.imslp.org/files/imglnks/...`). 판별 기준은 "302 여부" 가 아니라 **"`Location` 이 `*.imslp.org`
> 서브도메인 + `/files/` 경로인가"** 로 바뀌었다 — 맞으면 그 302 는 파일이고, 아니면(본체 `imslp.org`·`/friendlyredirect.html` 등)
> 여전히 게이트(쿠키·UA·IP 문제일 수 있다는 이전 판단이 그대로 적용된다)다. 이 규칙은 `HttpImslpClient.isFileHostRedirect()` 로
> 구현하고 `HttpImslpClientFileRedirectTest`(20건 — 실측 케이스, 알려진 파일 호스트 패턴, 게이트·면책 302, 위조·경계 호스트,
> null/빈 문자열)로 고정했다. **아직 Red 상태다** — 스텁은 항상 `false` 를 반환하고, backend-dev 가 판별 로직을 채우면서
> `resolveFileUrl()` 의 3xx 분기를 `getText()` 대신 이 함수로 가르도록 배선한다.

**근거**: 00 §6-1 — 파일 저장·JPA·관리자 인증을 그대로 재사용하고 Railway 서비스 하나로 운영. 비동기 워커+DB 폴링은 요청 스레드에서 15초를 기다리지 않게 하고(커넥션 고갈 방지) 재시작 복구를 단순하게 만든다.

### 3-1. 재발 방지 — 통합테스트는 `FakeImslpClient` 라 실제 IMSLP 응답 변화를 잡지 못한다 (2026-09-22 senior-dev)

이번 결함은 컴파일도 됐고 기존 테스트도 전부 초록이었다 — 위 표 "테스트 격리" 그대로 통합테스트가 `FakeImslpClient`(`@Primary`) 를 쓰기
때문에, `HttpImslpClient` 가 **실제 IMSLP 의 302 응답을 어떻게 다루는지는 테스트로 절대 검증되지 않는다.** 이번에도 픽스처가 아니라
실데이터를 크게(운영 로그 규모) 돌려서야 드러났다.

- **이 구조(픽스처로 격리)는 바꾸지 않는다.** 실네트워크를 치는 테스트는 느리고 불안정하고 IMSLP 에 부담을 준다는 근거(컨벤션 §6,
  위 표 "테스트 격리" 행)가 여전히 맞다. 바꿀 것은 "언제 알아차리는가" 이지 "테스트로 잡자" 가 아니다.
- **관측 지점은 이미 있다 — 새로 만들지 않는다.** `HttpImslpClient` 는 3xx·4xx·5xx·429 를 상태·host·location·retry-after 와 함께
  `WARN` 으로 로그한다(위 표 "로깅" 행, 이번 결함도 이 로그로 잡혔다). 별도 알림·대시보드는 1차 범위(관리자 1명, 수집도 관리자가
  개시하는 잡)에 과하다 — 지금 필요한 절차는 "3xx 인데 게이트로만 처리된 게 의심되면 이 `WARN` 로그부터 보고, §2-1 표를 다시
  실측한다" 는 한 줄이면 된다.
- **재발 방지의 실체는 판별 규칙을 순수 함수로 뽑아 20건 테스트로 고정한 것**이다(`isFileHostRedirect()`). IMSLP 가 다음에
  호스트 패턴을 또 바꿔도(새 서브도메인, 경로 변경) 손볼 곳이 이 함수 하나로 좁혀지고, 회귀 여부를 테스트가 바로 말해 준다.

## 4. 외부 HTTP 는 트랜잭션 밖 (컨벤션 §1)

- `CrawlWorker`/`EditionFileFetcher` 는 `@Transactional` 이 **없다**. 항목 처리 = `ImslpClient` 호출(트랜잭션 없음) → 결과 객체(`ParsedWorkPage`) → `CrawlPersistService.upsertWork(...)`(`@Transactional`, DB 만) → 파일 수신(트랜잭션 없음, 임시 파일) → `CrawlPersistService.attachFile(...)`(`@Transactional`) → 상태 갱신(`@Transactional`). 각 트랜잭션은 밀리초 단위.
- 저장 전략의 바이트 업로드(버킷 S3 호출)도 외부 I/O 이므로 트랜잭션 밖에서 먼저 하고, 그 결과로 `files`/`edition` 행을 쓴다. 삭제는 기존 `registerBytesDeletionAfterCommit` 패턴(커밋 후).
- 다운로드 API(02 §3-4): Resource 확보(외부/디스크 I/O) → 카운터 증가 트랜잭션 → 응답 스트리밍(트랜잭션 종료 후). `open-in-view: false` 유지.
- **`AdminEditionService` 는 클래스 레벨 `@Transactional(readOnly = true)` 를 걸지 않는다**(2026-09-07 검토 완료, senior-dev). 저장(§5-2·§5-3)의 쪽수 폴백이 저장소 읽기 + PDFBox 파싱이라, 클래스 기본 트랜잭션이 있으면 그 외부 I/O 가 트랜잭션 안에서 돈다. 대신 **얇은 진입점(외부 I/O) → `TransactionTemplate` 로 짧은 쓰기 트랜잭션** 구조를 쓰고 조회 메서드에는 `readOnly` 를 개별로 붙인다. 컨벤션 §1 의 기본형(클래스 `readOnly=true` + 쓰기 메서드 `@Transactional`)에서 벗어난 **의도된 예외**이며, 근거는 같은 §4 의 원칙("외부 I/O 는 트랜잭션 밖")이다. 다음 사람이 "컨벤션 위반" 으로 되돌리지 않도록 클래스 주석에도 같은 근거를 남겨 둔다.

## 7. 검색 구현 — QueryDSL + 정규화 컬럼 LIKE

**결정**
- 정규화: `SearchNormalizer`(01_ERD §2) — 엔티티 도메인 메서드(`changeTitle`, `addAlias`…)가 원문과 함께 `*_normalized` 를 갱신. 서비스는 setter 를 만지지 않는다.
- 조회: `WorkRepositoryImpl.search(SearchCondition, Pageable)` — 기존 `CommunityRepositoryImpl` 패턴(count 쿼리 + 페이지 쿼리 + IN 쿼리로 부속 데이터).
  1. `where`: 단어마다 `BooleanExpression termMatches(t)` = `work.titleKoNormalized.contains(t) OR work.titleOriginalNormalized.contains(t) OR composer.nameKoNormalized.contains(t) OR composer.nameOriginalNormalized.contains(t) OR JPAExpressions.selectOne().from(alias).where(alias.work.eq(work), alias.aliasNormalized.contains(t)).exists() OR (catalog EXISTS) OR (composerAlias EXISTS)` 를 **AND** 로 결합. `+ work.hidden.isFalse()` + 필터(level IN, 쪽수 구간은 `recommendedEdition.pageCount`, downloadable 은 `recommendedEdition.pdfFileId.isNotNull().and(recommendedEdition.koreaCopyright.eq(FREE))`).
  2. `orderBy`: `new CaseBuilder().when(titleKo == qn or aliasExactExists).then(3).when(titleKo startsWith qn or aliasPrefixExists).then(2).otherwise(1).desc()`, `work.downloadCount.desc()`, `work.id.asc()`.
  3. 페이지 결과의 id 목록으로 `work_alias`·`work_catalog_number` 를 IN 조회(별칭 원문·`matchedAlias` 계산·작품번호 목록) — N+1 방지.
  4. 작곡가 카드: 별도 쿼리(`composer` 에 같은 단어 AND 조건 + 공개 곡 EXISTS), `limit 3` + count.
  5. `unfilteredTotal`: 필터를 뺀 count 쿼리 1회(필터가 하나라도 있을 때만; 없으면 total 재사용).
- 작곡가 상세·관리 곡 목록도 같은 `WorkRepositoryCustom` 을 조건만 바꿔 재사용(숨김 포함 여부, 정렬 `opus`/`updatedAt`).
- 곡당 쿼리 수: 검색 1회 = count + page + alias IN + catalog IN + composer card (+ unfiltered count) = 5~6 쿼리. 수백 곡 규모에서 충분.

**근거**: 이미 QueryDSL 이 도입돼 있고(`QuerydslConfig`, `Projections`), 정규화 컬럼 방식은 DB 종류(H2/MySQL)·collation 에 기대지 않아 로컬/운영 결과가 같다. 풀텍스트 인덱스(MySQL FULLTEXT)는 H2 와 문법이 다르고 한글 부분 일치에 부적합.
**버린 대안**: DB `LOWER()/REPLACE()` 함수를 쿼리마다(인덱스 불가·H2/MySQL 함수 차이) / Elasticsearch·Lucene(서비스 추가, 1차 규모에 과함) / 애플리케이션 메모리 검색(재시작·다중 인스턴스 정합성).

## 10. SPA 라우트 등록 — HomeController catch-all + SecurityConfig 화이트리스트 (02 §0-5 확정)

## 12. 다운로드 실패 감지 — 클릭 시 HEAD 사전 확인 (2026-09-07 senior-dev)

**문제.** 화면 정의서 03 §동작·통신 상태는 "다운로드 시작 실패 → InlineAlert danger `지금은 파일을 받을 수 없어요…`" 를 요구하는데,
설계(02 §7)는 `<a href download>` 라 **실패를 알 방법이 없었다**. 그래서 인수조건이 통째로 구현되지 않았다(qa 결함 D5).

**결정.** 링크는 그대로 두고(네이티브 다운로드 유지), **클릭할 때 같은 주소로 `HEAD` 를 한 번 보내 결과를 본다.**
실패(4xx/5xx/네트워크 오류)면 버튼 아래 안내를 띄운다. 백엔드는 HEAD 에서 다운로드 수를 올리지 않는다(02 §3-4).

**대안과 기각 사유**

| 대안 | 기각 사유 |
|---|---|
| `fetch` 로 blob 을 받아 저장 | 100MB 파일을 메모리에 올린다. 02 §7 이 이미 금지 |
| `preventDefault()` → HEAD 확인 → 성공 시 `location.href` 로 재트리거 | 확인이 끝난 뒤 시작하니 느리고, 브라우저마다 "사용자 제스처가 아닌 다운로드" 취급이 다르다. 테스트도 브라우저 내비게이션에 의존하게 된다 |
| 다운로드 전용 사전 확인 API 신설 | 같은 판정을 두 곳에서 하게 된다. HEAD 는 이미 "본문 없는 GET" 이라는 표준 의미가 있다 |
| 그대로 두고 10초 뒤 버튼만 복구 | 실패를 **모른다**. 정의서 문구를 띄울 수 없다 |

**대가.** 성공 시 요청이 2번(HEAD + 브라우저 GET) 간다. HEAD 는 바이트를 보내지 않아 비용이 작고,
실패 시 브라우저의 다운로드 실패와 화면 안내가 함께 뜨는 것은 정의서(버튼은 다시 활성, 안내는 화면에)와 어긋나지 않는다.
버튼 문구는 확인이 진행되는 동안만 `받는 중…` 이고, 확인이 끝나면 원래대로 돌아온다(정의서의 "최대 10초 후 자동 복귀" 는
감지 수단이 생겼으므로 타이머 폴백이 필요 없다).

> **2026-09-21 보강 — §28.** 위의 마지막 괄호는 **"실패 감지 수단으로서의 타이머"** 를 기각한 것이고 그대로 유효하다.
> 다만 §28 에서 진행 중 `disabled` 를 붙이면서 10초가 **다른 일**로 되살아난다: 응답이 영영 오지 않는 요청이
> 버튼을 영구히 잠그는 것을 푸는 **자물쇠 해제 장치**다(감지기가 아니다). 그래서 10초 복귀는 실패로 치지 않는다.

## 13. 관리 화면 세션 만료 안내는 AdminRoute 가 맡는다 (2026-09-07 senior-dev)

00 §4·05 공통 표의 `로그인이 풀렸어요…` + `작성 중이던 내용은 저장되지 않았어요` → 2초 후 로그인 화면(복귀 파라미터)은
**관리 화면 공통 가드 `AdminRoute`** 에서 구현한다. 화면마다 붙이면 새 관리 화면에서 빠지고, 정의서가 요구하는 것도 화면별 동작이 아니다.

배선은 이미 있다: `lib/http.js` 가 재발급 실패 시 `window` 에 `auth:expired` 를 발행하고 `AuthContext` 가 게스트로 강등한다.
`AdminRoute` 는 그 이벤트를 구독해 안내를 띄우고 2초 뒤 `/login?redirect={원래 경로}` 로 보낸다.
**판단 순서가 중요하다** — 만료 안내를 `!isAuthenticated → <Navigate>` 보다 먼저 처리해야 한다(강등이 같은 순간에 일어나므로,
순서가 뒤바뀌면 안내 없이 곧바로 튕긴다).

## 14. 통합테스트 기반 두 가지 — 트랜잭션 있는 것과 없는 것 (2026-09-07 senior-dev)

`ApiIntegrationTestSupport` 는 클래스에 `@Transactional` 이 걸려 있다(빠르고 격리가 공짜다). 그런데 그 때문에
**테스트 스레드에 영속성 컨텍스트가 열린 채로 컨트롤러가 돌아**, 운영(`open-in-view: false`)에서만 터지는 결함을 못 잡는다.
실제로 `GET /api/communities/{id}` 는 운영에서 전건 500(`LazyInitializationException`)인데 통합테스트는 초록이었다(qa 결함 D2).

- 새 기반 `NonTransactionalApiTestSupport`(`@Transactional(NOT_SUPPORTED)` + 격리 H2 `nontxdb` + `@AfterEach` 테이블 정리)를 둔다.
- **사용자에게 노출되는 대표 GET** 은 `PublicReadApiWithoutTestTransactionIntegrationTest` 에서 이 기반으로 한 번씩 통과해야 한다
  (커뮤니티 상세·댓글 목록, 곡 상세·검색·인기, 작곡가 목록/상세/곡, 다운로드).
- **기존 테스트를 전부 옮기지는 않는다.** 롤백이 주는 격리·속도를 잃는 비용이 크고, 대표 엔드포인트 한 벌이면
  "열린 세션에 기대는 코드" 는 잡힌다. 새 조회 API 를 추가하면 이 클래스에 한 줄 추가하는 것이 규칙이다.
- 부수효과 중 **커밋 이후에만 일어나는 것**(저장 바이트 삭제 = `afterCommit`)은 트랜잭션 기반 테스트에서 관찰할 수 없다.
  판본 파일의 "옛 행 삭제"(02 §5-3·§5-5·§4-9)는 `AdminApiTestSupport.fileRowExists()` 로 **files 행만** 확인한다
  (02 §3-4 이후 공용 파일 API 로는 판본 파일을 조회할 수 없다).

## 14-2. `CommunityDTO` 의 `imageUrls`/`attachments` — 필드를 뺀다 (2026-09-07 senior-dev, qa 2차 결함)

`CommunityService.getCommunityDetail` 이 `CommunityDTO.from(community, List.of(), List.of())` 로,
목록(`CommunityRepositoryImpl`)은 `from(entity)` 로 부른다 — **두 경로 모두 항상 빈 배열**이다.
화면은 첨부를 `GET /api/files?refId=…&refType=COMMUNITY&usage=ATTACHMENT` 로 따로 받으므로 사용자에게 보이는 문제는 없다.

- **채우지 않는다.** 채우면 상세·목록마다 파일 조회가 한 번씩 더 붙고, 프론트가 이미 쓰는 `/api/files` 와 **같은 사실을 내려주는 두 번째 출처**가 생긴다.
  두 출처가 생기면 삭제·업로드 직후 어느 쪽을 믿을지가 스택마다 갈린다.
- **뺀다.** 항상 `[]` 인 필드는 없는 필드보다 나쁘다 — "첨부가 없다" 고 **거짓말을 하는 계약**이라, 나중에 붙는 클라이언트(특히 Flutter 앱)가
  여기에 바인딩하면 첨부가 있는 글을 첨부 없는 글로 그린다. 지금 지우는 비용은 필드 2개 + `from` 오버로드 1개 + 호출부 2곳이다.
- 커뮤니티는 §9(01 §9 8-2)에서 "유지만" 이지만, 이건 기능 변경이 아니라 **죽은 계약 제거**이고 관찰되는 동작은 바뀌지 않는다
  (프론트에 `imageUrls` 사용처 0곳, 문서에 언급 0곳, 기존 테스트에 단언 0곳 — 확인함). 커뮤니티에 다시 손대는 유일한 건이다.
- 함께 지운다: `CommunityDTO.FileInfoDTO` 중첩 클래스(이 필드 전용이라 다른 사용처가 없다).

## 14-3. §5-7 fetch-file 의 라이선스 분기·409 를 테스트로 덮는 방법 (2026-09-07 senior-dev)

qa 지적: `imslpFileId`/`imslpLicenseCode` 는 **수집 워커만** 채우고 `EditionSaveDTO`(§5-2·§5-3)로는 설정할 수 없어,
"재배포가 허용되지 않는 표기라 받아올 수 없어요"(400)와 QUEUED 중복(409)에 **통합테스트로 도달할 수 없다**.

- **`EditionSaveDTO` 에 `imslpFileId`/`imslpLicenseCode` 를 열지 않는다.** 이 두 값은 "IMSLP 가 그렇게 말했다" 는 사실의 사본이고,
  사람이 손으로 고칠 수 있게 하면 라이선스 판단의 근거가 관리자의 오타로 바뀔 수 있다(01 §9-1 의 재배포 조건이 이 값에 걸려 있다).
  판정은 이미 `koreaCopyright`/`copyrightNote` 라는 사람용 필드가 따로 있다.
- **테스트 전용 API·프로파일 분기도 두지 않는다**(운영에 없는 경로를 테스트가 지탱하게 된다).
- **도달 경로는 이미 있다: 수집 픽스처**. `CrawlTestSupport` + `FakeImslpClient` 로 수집을 한 번 돌리면 판본에 `imslpFileId`·`imslpLicenseCode` 가 실제 경로로 채워진다.
  픽스처에 **재배포 불가 라이선스(예: `imslp_licence = Non-PD US`/CC BY-NC-ND) 판본이 있는 작품 페이지**를 하나 추가하면
  400 분기가 덮이고, 409 는 `fetchFiles=false` 로 수집한 뒤 같은 판본에 `fetch-file` 을 **두 번 연속** 호출하면(`FakeImslpClient.holdFiles` 로 첫 요청을 QUEUED/FETCHING 에 붙잡아 두고) 덮인다.
  → 이번 라운드의 6건에는 포함하지 않는다(픽스처 추가 = 계약 변경이 아니라 테스트 보강). **다음 라운드에 senior-dev 가 픽스처와 테스트를 추가한다.**

## 16. 저작권 자동 판정 실행 구조 (2026-09-07 senior-dev)

규칙 자체는 기획 `02_저작권_판정_지침.md` 부록 A, 계약은 `02_API_명세서.md` §5-11·§5-12.

- **동기 요청 하나로 끝낸다** — 비동기 잡(수집 워커 같은 구조)을 만들지 않는다. 대상이 판본 1,792건이고
  외부 I/O 가 전혀 없다(전부 우리 DB 안의 값 비교). 읽기 + UPDATE 몇 천 건은 수백 ms 다.
  잡을 만들면 상태 테이블·폴링 화면·재시작 복구가 따라오는데, 얻는 것이 없다.
- **판정 규칙은 순수 함수로 분리한다** — `CopyrightAutoJudge`(가칭, `sheetmusic/edition` 패키지) 에
  `judge(licenseCode, composerDeathYear, editor, arranger, kind, publishYear, currentYear)` →
  `FREE + 규칙코드` 또는 `UNKNOWN + 사유코드` 를 돌려주는 함수를 둔다. 이유 두 가지:
  ① §5-8 대기함의 `autoJudgeSkipReason` 과 §5-11 이 **같은 함수**를 써야 "대기함에 EDITOR_UNVERIFIABLE 로 보이는데
  실행하면 열린다" 같은 어긋남이 안 생긴다. ② 6가지 분기의 경계값(70년·120년)을 컨트롤러 통합테스트로만 덮으면
  판본을 6개씩 만들어야 해서 테스트가 비싸다 — 컨벤션 §6 의 "순수 유틸/알고리즘은 작은 단위테스트 허용" 예외에 해당한다.
- **`currentYear` 는 주입한다**(컨벤션 §6: 시간 의존 로직은 시간을 파라미터로). 서비스가
  `Year.now(ZoneId.of(app.timezone))` 로 구해 함수에 넘긴다. 기준 연도 1906 같은 상수를 코드에 박지 않는다.
- **트랜잭션 하나**. `dryRun` 은 계산만 하고 저장 호출을 하지 않는 방식으로 구현한다(트랜잭션 롤백으로 흉내 내지 않는다 —
  롤백 방식은 예외로 성공 응답을 만드는 셈이라 읽기 어렵고, `@Transactional` 경계와 싸운다).
- **`system:auto` 는 상수로 한 곳에만 둔다**(`EditionEntity` 나 `CopyrightAutoJudge` 의 `public static final`).
  §5-11(쓰기)·§5-12(되돌리기)·화면 표시가 같은 문자열을 봐야 한다. 사용자 username 에는 `:` 가 들어갈 수 없어 충돌하지 않는다.
- 대량 UPDATE 는 JPA 더티체킹으로 충분하다(수천 건, 배치 인서트 설정 이미 있음). 벌크 JPQL 로 최적화하지 않는다 —
  판정마다 note 문구가 달라 어차피 행 단위다.

### 16-1. 트랜잭션은 **하나가 아니라 청크**다 (2026-09-07 정정, senior-dev)

위의 "트랜잭션 하나"는 대상 1,792건을 전제로 쓴 것이다. 곡을 300개로 늘리면 판본은 **25,000개**가 되고, 이때
"UNKNOWN 판본 전량을 한 트랜잭션에서 읽고 고친다"가 두 가지를 깨뜨린다.

1. **수집 워커와 같은 행을 놓고 부딪힌다.** 워커는 `CrawlPersistService` 로 짧은 트랜잭션을 계속 여닫으며
   같은 `edition` 행을 UPDATE 한다(재수집). 자동 판정이 수천 행의 쓰기 락을 수 초 이상 붙들고 있으면
   워커 쪽이 락 대기 → 타임아웃으로 죽고, 그 항목은 `INTERNAL_ERROR` 가 된다. 수 시간짜리 수집 중에
   관리자가 자동 판정을 누르는 것은 **정상적인 사용 흐름**이라 "그때는 누르지 마세요"로 막을 수 없다.
2. 영속성 컨텍스트에 25,000 엔티티(+ 곡·작곡가 fetch join)를 올린 채 더티체킹을 돌린다.

**결정**: 대상 판본 id 를 먼저 읽고(가벼운 조회), **N건(기본 500)씩 별도 트랜잭션**으로 판정·저장한다.
응답 숫자(§5-11 계약)는 청크 합계로 그대로 만든다. 중간에 실패해도 앞 청크는 커밋된 채 남지만,
자동 판정은 `UNKNOWN → FREE` 한 방향 멱등이라 **다시 실행하면 이어서 진행된다**(§5-11 의 재실행 안전 계약).
추천 자동 지정도 같은 방식으로 곡 단위 청크로 돈다. `dryRun` 은 지금처럼 저장을 호출하지 않는다.

> 이건 성능 최적화가 아니라 **동시성 계약**이다. "수집이 도는 동안에도 자동 판정이 안전하다"가 지켜야 할 성질이고,
> 그것을 지키는 가장 싼 방법이 청크다(잡·큐를 만들자는 얘기가 아니다 — §16 의 결론은 그대로다).

## 17. 로컬 DB 를 파일 H2 로 영속화 — 컨벤션 §5-2 의 **명시적 예외** (2026-09-07 senior-dev)

> 컨벤션 §5-2: "로컬 H2는 특별한 지시가 없으면 재시작(매 기동 초기화)이다. **데이터를 남기려면 그 모듈에 명시적 사유를 적는다(예외).**"
> 이 문서가 그 사유다. 컨벤션 문서는 고치지 않는다 — 원칙은 그대로고, 이 모듈이 예외를 쓰는 것이다.

### 17-1. 사유
로컬 DB 에 들어 있는 것은 우리가 만든 더미가 아니라 **외부 사이트(IMSLP)에서 규칙을 지켜 가며 받아온 데이터**다.
1차 수집은 20곡·판본 1,792개·PDF 47개(228MB)를 받는 데 IMSLP 요청 수백 건과 수 시간을 썼다(요청 간격 2초, 파일당 15초 대기).
인메모리 DB 라 **서버를 한 번 껐다 켜면 이게 전부 사라지고**, 코드를 한 줄 고칠 때마다 IMSLP 에 같은 부담을 다시 준다.
이건 재현성 문제가 아니라 **외부 사이트에 대한 예의 문제**이고, 기획 §9-1(수집 예절)과 정면으로 어긋난다.
컨벤션이 인메모리를 기본으로 삼은 이유("깨진 시드·스키마 잔재를 원천 차단")는 우리가 **언제든 파일을 지우면 초기화된다**는
탈출구를 문서화하는 것으로 대체한다(17-4).

### 17-2. 설정 (backend-dev 가 `src/main/resources/application.yml` 에 적용)
```yaml
spring:
  datasource:
    url: jdbc:h2:file:${LOCAL_DB_PATH:./data/devdb};MODE=MySQL;DB_CLOSE_ON_EXIT=FALSE;AUTO_SERVER=TRUE
  jpa:
    hibernate:
      ddl-auto: update      # create 면 매 기동 스키마가 날아가 파일 DB 가 무의미하다
```
- `AUTO_SERVER=TRUE`: 앱이 떠 있는 동안 H2 콘솔·다른 프로세스가 같은 파일을 열 수 있다(파일 잠금 충돌 방지).
- `LOCAL_DB_PATH` 환경변수로 경로를 바꿀 수 있게 둔다(컨벤션 §5-1 — 환경 차이는 환경변수로).
- **`prod` 프로파일은 그대로 MySQL** 이다. 이 변경은 로컬 기본 프로파일에만 영향을 준다.
- **`src/test/resources/application.yml` 은 건드리지 않는다.** 테스트는 계속 `jdbc:h2:mem:testdb` + `create-drop` 로 격리된다
  (컨벤션 §6: 순서·상태 의존 테스트 금지).

### 17-3. `data-*.sql` 재실행 문제와 해법
`spring.sql.init.mode: always` 는 **매 기동** 시드 스크립트를 다시 돌린다. 파일 DB 에서는 이게 전부 깨진다:
`data-users.sql`(명시 id 1~111) → PK 충돌로 **기동 실패**, `data-comment.sql`(id 없음) → 매 기동 댓글 중복 누적,
`data-rooms.sql`(`DELETE FROM chat_room` 후 재삽입) → 메시지가 있으면 FK 위반,
`data-h2-reset-identity.sql`(`RESTART WITH 1000`) → 이미 1000번대 행이 있으면 이후 INSERT 가 PK 충돌.

- **스크립트를 멱등하게 고치는 방향은 버린다.** 이건 **데모 데이터**(가짜 사용자·게시글)라 원래 "새 DB 에 1회" 가 맞는
  성격이다(컨벤션 §5-2 의 "데모/개발용 데이터"). MERGE 로 고쳐도 identity 리셋 문제는 안 풀리고, 테스트가 의존하는
  시드 내용(사용자 111명·ADMIN 역할)을 건드릴 위험만 커진다.
- **`mode: never` 로 못 박는 방향도 버린다.** 그러면 새로 만든 파일 DB 에 시드 계정이 없어 **로컬 관리자 로그인
  (`gks930620`)이 불가능**하다.
- **채택: DB 파일이 이미 있으면 시드 스크립트를 건너뛴다.** `EnvironmentPostProcessor`(가칭 `LocalDbInitModePostProcessor`)
  하나를 두고,
  - `spring.datasource.url` 이 `jdbc:h2:file:` 로 시작하지 **않으면 아무것도 하지 않는다**(테스트·운영에 영향 0),
  - 시작하면 URL 에서 파일 경로를 뽑아 `{경로}.mv.db` 존재 여부를 보고
    **있으면 `spring.sql.init.mode=never`, 없으면 `always`** 를 최우선 property source 로 넣는다.
  - 등록은 `src/main/resources/META-INF/spring.factories` 의 `org.springframework.boot.env.EnvironmentPostProcessor`
    키다 (2026-09-07 정정 — 처음 이 문서는 `META-INF/spring/….EnvironmentPostProcessor.imports` 로 적었으나 **틀렸다**).
    근거: Boot 3.3.4 의 `EnvironmentPostProcessorsFactory.fromSpringFactories` 는
    `SpringFactoriesLoader.forDefaultResourceLocation`(= `spring.factories`)만 읽고, `META-INF/spring/*.imports` 는
    자동설정(`AutoConfiguration.imports`) 전용 경로라 무시된다 — 실제로 `.imports` 로 등록했을 때 프로세서가 아예
    돌지 않아 Red 가 그대로 유지됐다(backend-dev 바이트코드 확인).
  - **순서**: `ConfigDataEnvironmentPostProcessor`(order `HIGHEST_PRECEDENCE + 10`) **뒤**에 돌아야 yml 의
    `spring.datasource.url` 을 볼 수 있다 → `getOrder()` 를 `LOWEST_PRECEDENCE` 로.
  - `if (로컬) … else …` 코드 분기가 아니라 **"이 URL 이면 이 설정"** 이라는 설정 계산이라 컨벤션 §5 취지에 맞는다.
- CSV 시드 로더(`SeedLoader`, 01_ERD §6)는 이미 멱등·삽입 전용이라 그대로 매 기동 돈다. 두 번째 기동부터는 no-op 다.

### 17-4. 초기화 방법 (`ddl-auto: update` 의 잔재 대응 — README 성격의 안내)
`update` 는 컬럼·테이블을 **추가만** 하고 이름 변경·삭제·타입 축소를 반영하지 않는다. 엔티티를 고치다 보면
쓰지 않는 컬럼이 남고, `NOT NULL` 추가 같은 변경은 기존 행 때문에 실패한다. 이럴 때는 **파일을 지운다**:

```
1) 서버를 끈다 (파일 잠금 해제)
2) 프로젝트 루트의 data/ 폴더를 지운다   (devdb.mv.db, devdb.trace.db)
3) 서버를 다시 켠다 → 스키마 새로 생성 + data-*.sql 재적재 + CSV 시드 재적재
   (수집 데이터는 사라진다 — 다시 받아야 한다)
```
- 스키마를 자주 바꾸는 작업(엔티티 설계 중)에는 `SPRING_DATASOURCE_URL=jdbc:h2:mem:devdb;MODE=MySQL` 로 띄워
  예전처럼 휘발로 쓸 수 있다. 위 PostProcessor 가 mem URL 을 그냥 통과시키므로 시드도 정상 적재된다.
- `.gitignore` 에 `/data/` 를 넣는다. **DB 파일은 절대 커밋하지 않는다**(수백 MB PDF 메타 + 로컬 계정 해시).
- 업로드된 PDF 바이트는 이미 `./uploads` (`file.upload-dir`, 로컬 폴백 저장소)에 있고 `.gitignore` 대상이다.
  DB 만 지우고 `uploads/` 를 남기면 **참조 없는 파일**이 되므로, 초기화할 때는 `uploads/` 도 함께 지운다.

### 17-5. 스키마 드리프트는 테스트가 못 잡는다 — 엔티티 변경 규칙 (2026-09-07 senior-dev)

테스트는 인메모리 H2 + `ddl-auto: create-drop` 이라 **언제나 엔티티와 100% 일치하는 새 스키마**에서 돈다.
반면 로컬 파일 DB 와 운영 MySQL 은 `update` 다. 즉 **"테스트 324개 전부 통과인데 기동한 서버만 깨지는"** 변경이 존재한다.

| 엔티티 변경 | `update` 의 실제 동작 | 테스트가 잡나 |
|---|---|---|
| 컬럼 **추가**(nullable) | `ALTER TABLE ADD COLUMN` — 안전 | — |
| 새 테이블·인덱스 추가 | `CREATE TABLE` — 안전 | — |
| 컬럼 **추가(NOT NULL, 기본값 없음)** | 기존 행이 있으면 H2 는 실패(기동 실패), MySQL 은 암묵 기본값으로 채움(조용한 오염) | **못 잡는다** |
| `@Column(length)` **축소**, 타입 변경, 이름 변경, 삭제 | **아무 일도 일어나지 않는다** — DB 는 옛 정의 그대로, 코드만 새 값을 믿는다 | **못 잡는다** |
| `nullable = false` → `true` (**NOT NULL 해제**) | **아무 일도 일어나지 않는다** — DB 는 계속 NOT NULL 이라 NULL 을 쓰는 코드가 런타임에 500 | **못 잡는다** |
| **enum 상수 추가**(`@Enumerated(STRING)` 필드의 자바 enum 에 값 하나 더) — **2026-09-08 추가** | **아무 일도 일어나지 않는다.** 그런데 그 컬럼은 `varchar` 가 아니라 네이티브 `ENUM('A','B')` 다(§17-6) — 새 값이 든 행을 읽는 **조회 자체가** `Value not permitted for column "('A','B')": "C" [22030-224]` 로 터진다. 기동 중에 도는 코드면 **애플리케이션이 뜨지 못한다** | **못 잡는다** |

**규칙**
1. 엔티티 변경은 **추가(nullable) 위주**로 한다. 이번 권고인 `edition.admin_edited_at`(nullable)·`seed_load`(새 테이블)는
   둘 다 안전한 쪽이라 **살아 있는 수집 데이터를 지우지 않고 적용된다**.
2. **비추가형 변경(위 표의 아래 세 줄)은 마이그레이션 문장을 문서에 남긴다 — 규칙이다 (2026-09-08 강화).**
   추가형(nullable 컬럼·새 테이블·인덱스)이 아닌 모든 엔티티 변경은 `01_ERD.md` **§9 마이그레이션 대장**에
   `날짜 / 변경 / H2 문장 / MySQL 문장 / 안 하면 무슨 증상` 다섯 칸을 채워 한 줄로 남긴다. 로컬 초기화(§17-4)로 대체할 수 있어도
   **문장은 적는다** — 운영 DB 는 지울 수 없기 때문이다. 적지 않으면 다음 사람의 로컬 DB 와 운영 DB 는 조용히 어긋난 채로 남고,
   테스트는 `create-drop` 이라 끝까지 초록이다.
   - 실제로 이렇게 새어 나갔다: `download_log.edition_id` NOT NULL 해제(01_ERD §3-7)를 계약·테스트·구현까지 다 하고도
     문장을 안 남겨, **기존 DB 에서만 판본 삭제가 500** 이었다(backend-dev 재현). 대장 첫 줄이 그 건이다.
   - 리뷰 체크리스트: 엔티티 diff 에 `nullable`·`length`·컬럼명·타입 변경이 있으면 **§9 대장 줄이 같은 변경에 포함돼 있는지** 본다.
3. 운영은 첫 배포 이후 `update` 에 계속 기대지 않는다 — 컬럼 축소·삭제가 필요해지는 시점에 마이그레이션 도구
   (Flyway)를 도입한다. 지금 도입하지 않는 이유는 아직 운영 DB 가 없어서지, `update` 가 충분해서가 아니다.

### 17-6. enum 컬럼은 네이티브 `ENUM` 이 아니라 `VARCHAR` 로 못 박는다 (2026-09-08 senior-dev)

**터진 일.** `SeedType` 에 상수 `COLLECTION_GUIDE` 를 하나 추가했더니 **살아 있는 로컬 DB 에서 애플리케이션이 기동조차 못 했다**
(backend-dev 재현): `Value not permitted for column "('COMPOSER','WORK')": "COLLECTION_GUIDE" [22030-224]` → `SeedLoader` 예외.
기존 DB 의 `seed_load.seed_type` 이 네이티브 `ENUM('COMPOSER','WORK')` 로 만들어져 있었고 `ddl-auto: update` 는 enum 정의를 넓히지 않는다.
값을 **쓰기** 전에 그 컬럼을 **읽는** 순간 깨진다는 점이 고약하다 — "새 값을 안 쓰면 괜찮다"가 성립하지 않는다.

**왜 그렇게 만들어지나.** 우리는 `@Enumerated(EnumType.STRING)` 만 썼는데, Hibernate 6 은 H2·MySQL 에서 이 매핑의 **DDL 타입을
네이티브 `enum(...)` 으로** 낸다(`EnumJavaType.getRecommendedJdbcType` → 레지스트리에 `ENUM` 이 있으면 무조건 그것,
`H2Dialect/MySQLDialect.getEnumTypeDeclaration`). `@Column(length = 30)` 은 무시되고, `hibernate.type.prefer_native_enum_types=false`
로도 꺼지지 않는다(그 설정은 `@Enumerated(STRING)` 경로를 타지 않는다 — 6.5.3 소스 확인). **우리가 고른 적 없는 기본값**이다.

**결정: 16개 enum 컬럼 전부를 `@JdbcTypeCode(SqlTypes.VARCHAR)` 로 VARCHAR 고정한다.** 대상·마이그레이션 문장은 `01_ERD.md` §9-1.

**근거**
1. **enum 상수 추가는 우리가 앞으로 가장 자주 할 스키마 변경**이다. `crawl_item.fail_reason`(수집 실패 유형), `edition.imslp_license_code`,
   `work.hidden_reason`(지금 값이 **하나뿐**이다), `files.ref_type`(새 도메인이 파일을 붙일 때마다 늘어난다) — 전부 늘어날 자리다.
   지금 구조에서는 그 한 줄짜리 코드 변경이 **매번 16개 컬럼짜리 지뢰밭 위의 비추가형 마이그레이션**이고, 잊으면 기동 실패다.
2. **실패가 가장 나쁜 방식으로 난다.** 컴파일도 테스트도 통과하고(테스트는 `create-drop`), 배포 후 기동에서 죽는다.
   §17-5 가 경고한 "테스트가 못 잡는 변경" 중에서도 유일하게 **런타임 500 이 아니라 프로세스 기동 실패**까지 가는 유형이다.
3. **네이티브 ENUM 이 주는 이득이 사실상 없다.** 값 제약은 이미 세 겹으로 지켜진다 — DTO 검증(02 §0), `@Enumerated(STRING)`(자바 enum 밖의
   값을 쓸 수 없다), 읽을 때 Hibernate 가 상수로 변환(모르는 값이면 예외). DB 는 이 앱만 쓴다. 저장 공간 이득도 varchar(30) 대비 무의미하다.
   반대로 MySQL 의 ENUM 은 `ORDER BY` 가 **선언 순서(ordinal)** 로 동작해서, 나중에 값을 중간에 끼워 넣으면 정렬이 조용히 바뀌는 함정까지 있다
   (지금은 난이도 정렬을 `CASE` 로 명시해 피하고 있다 — 02 §3-2).
4. **지금이 가장 싼 시점이다.** MySQL 에서 이 ALTER 는 테이블 재작성인데, **운영 DB 가 아직 없다.** 로컬 DB 하나만 고치면 끝난다.
   나중에 데이터가 쌓인 뒤에 하면 같은 판단을 훨씬 비싸게 실행하게 된다.

**대안으로 검토하고 버린 것**
- *`columnDefinition = "varchar(30)"`*: 되긴 하지만 DDL 문자열을 엔티티에 박아 방언 이식성을 잃고, `length`·`nullable` 등
  다른 매핑 정보가 무시되어 두 곳이 어긋난다. `@JdbcTypeCode` 는 **타입만** 고르고 나머지는 JPA 매핑이 그대로 쓴다.
- *전역 설정 한 줄*: 위에서 본 대로 6.5 에는 이 경로를 끄는 설정이 없다. (있어도 "설정 파일 한 줄로 스키마 모양이 바뀌는" 구조는
  다음 사람이 엔티티만 보고는 알 수 없어 선호하지 않는다.)
- *그대로 두고 대장에만 적기*: 규칙이 지켜지려면 사람이 매번 "이 enum 에 값을 더하면 비추가형" 임을 기억해야 한다.
  이번에 이미 한 번 놓쳤다. 구조로 없앨 수 있는 규칙은 구조로 없앤다.

**회귀 가드(senior-dev 작성, Red)**: `SchemaEnumColumnTypeIntegrationTest` — 부팅된 스키마의 `INFORMATION_SCHEMA.COLUMNS` 에
`DATA_TYPE = 'ENUM'` 인 컬럼이 **0개**여야 한다. 컨벤션 §6 의 "컨트롤러 통합테스트만" 에 대한 예외로 두는 이유:
이 결함은 요청/응답에 전혀 드러나지 않고(모든 API 가 초록이었다) 오직 **엔티티가 만드는 DDL** 에만 나타난다.
새 엔티티가 enum 을 추가할 때 이 테스트가 실패하면, 그 자리에서 `@JdbcTypeCode` 를 붙이면 된다.

## 18. 홈 인기곡 tie-breaker — 큐레이션 노출 순서를 쓰지 않는다 (2026-09-08 senior-dev)

**기획 §11-3 이 senior-dev 에게 되돌린 질문**: 정렬 2순위인 "큐레이션 노출 순서"(`03_1차_큐레이션_곡목록.md` 의 `#` 열)
값이 데이터에 있는가. **없다.** `src/main/resources/seed/works.csv` 에 `seq` 열은 있지만
`WorkEntity`·`work` 테이블에 대응 컬럼이 없고 `SeedService` 도 그 열을 읽지 않는다.

**결정: 기획 §11-3-5 의 대안을 채택한다 — `level ASC(BEGINNER→ELEMENTARY→INTERMEDIATE→ADVANCED, NULL 마지막) → title_ko 가나다 → id ASC`.**
`seq` 는 CSV 에 사람이 읽을 값으로만 남기고 컬럼으로 싣지 않는다.

**근거**
1. **큐레이션 순서가 담고 있는 판단이 곧 난이도 순서다.** 기획 §11-3-5 자신이 "`03` 의 곡 번호는 이미 입문(1–2) → 초급(3–15) →
   중급(16–35) → 고급(36–50) 순"이라고 적었고, 이 tie-breaker 로 이루려던 결과("다운로드가 0인 초기에 홈 첫 10칸이 입문·초급으로")는
   난이도 오름차순으로 **그대로** 달성된다. 같은 결과를 얻는 두 방법 중 데이터를 늘리지 않는 쪽을 고른다.
2. **`seq` 는 시드 50곡에만 있는 값이다.** 인기곡 모집단은 시드 곡이 아니라 **공개된 전체 곡**이고, 수집으로 들어오는 곡(수백 건)과
   관리자 직접 등록 곡에는 `seq` 가 영원히 없다. 그 곡들은 전부 "NULL = 맨 뒤"로 뭉쳐 사실상 tie-breaker 가 없는 상태가 된다 —
   규칙이 모집단의 일부에만 적용되면 "왜 이 순서인가"를 아무도 설명할 수 없다. 난이도는 모든 곡이 갖는 값이다.
3. **`seq` 는 문서 표의 행 번호라 재정렬에 취약하다.** 03 문서가 검수로 갱신되어 곡이 하나 삽입되면 뒤 49곡의 번호가 밀리고,
   홈 첫 화면 순서가 **문서 편집만으로** 조용히 바뀐다. 저장된 데이터의 뜻이 문서 편집 이력에 종속되면 안 된다.
4. **기존 DB 를 채울 방법이 없다.** 시드 로더는 `seed_load` 기록이 있는 행을 건너뛰므로(01_ERD §3-10),
   컬럼을 추가해도 **이미 적재된 50곡은 NULL 로 남는다.** 채우려면 "적재 기록이 있어도 이 컬럼만 백필" 이라는
   예외 경로를 시드 로더에 하나 더 뚫어야 한다 — tie-breaker 하나를 위해 치를 값이 아니다.
   (같은 이유로 이번에 실제로 필요한 `collection_guide` 는 **백필 경로를 명시적으로 설계했다** — 02 §3-3·01_ERD §6. 그 값은
   사용자 화면에 문장으로 나가는 것이라 없으면 화면이 빈다. tie-breaker 는 없어도 화면이 비지 않는다.)
5. tie-breaker 가 실제로 작동하는 구간은 **다운로드가 전부 0인 초기**뿐이다. 기록이 쌓이면 1순위(다운로드 수)가 지배한다.
   수명이 짧은 규칙에 스키마·시드·로더 세 곳을 바꾸는 것은 비용이 이익보다 크다.

**부작용 점검**: 난이도 오름차순이 "난이도를 인위적으로 섞는 별도 규칙"(§11-3-5 가 경계한 것)이 되지는 않는다 —
섞는 게 아니라 **한 방향으로 세우는** 것이고, 기획이 대안으로 직접 제시한 규칙이다. 규칙은 여전히 하나이므로
"어느 쪽이 이겼는지 설명 못 하는" 상황도 생기지 않는다.

## 19-1. 그 게이트가 요청마다 쿼리 2회인 것 — 알고 있으나 지금은 미룬다 (2026-09-09 senior-dev, qa 5차 코드리뷰)

**사실(8084 실측 로그, `server-8084.log`).** 오늘 하루 이 로그의 **ERROR 61건이 전부 클라이언트 단절이다(61/61, 100%)**.
그중 **60건이 미리보기 PNG**(`GET /uploads/*.png`), 1건이 PDF 다운로드였다. 즉 다운로드 취소 같은 특수 상황이 아니라
**목록 화면을 보다가 다른 화면으로 넘어가는 평범한 사용**이 에러 로그를 채우고 있다. 단절 1회가 남기는 것은 세 줄이다:

1. `ERROR c.t.t.c.e.GlobalExceptionHandler - Unexpected Exception:` + 전체 스택
   (`AsyncRequestNotUsableException: ServletOutputStream failed to write: java.io.IOException: Connection reset by peer`)
2. `WARN o.s.w.s.m.m.a.ExceptionHandlerExceptionResolver - Failure in @ExceptionHandler ...#handleException(Exception)` + 전체 스택
3. `WARN o.s.w.s.m.s.DefaultHandlerExceptionResolver - Resolved [...AsyncRequestNotUsableException...]`

**2차 예외의 정체는 "끊긴 커넥션에 쓰기 실패" 가 아니다** — 실측 메시지는
`HttpMessageNotWritableException: No converter for [class ErrorResponse] with preset Content-Type 'image/png'` 다.
바이트 엔드포인트는 응답 Content-Type 이 이미 `image/png`·`application/pdf` 로 정해진 뒤에 본문을 쓰다가 끊기므로,
그 자리에서 **JSON 에러 본문을 만들려 한 것 자체**가 2차 예외의 원인이다. → **본문을 만들지 않으면 2·3번이 함께 사라진다.**

**왜 고치나.** 이 제품의 주기능이 대용량 PDF 전송이고 목록마다 미리보기 이미지를 뿌린다. 사용자 취소·페이지 이탈은
**정상 동작**이다. 지금은 에러 로그의 신호 대 잡음비가 0 이라, 진짜 오류가 들어와도 61건 사이에 묻힌다.
운영에서 "ERROR 가 나면 본다" 는 규칙을 유지하려면 정상 동작이 ERROR 를 찍지 않아야 한다.

### 20-1. 결정

| 항목 | 결정 |
|---|---|
| 단절 판별 | `org.springframework.web.util.DisconnectedClientHelper.isClientDisconnectedException(e)` (스프링 제공, public) |
| 처리 진입점 | `GlobalExceptionHandler` 에 `@ExceptionHandler(IOException.class)` **하나**. 단절이면 조용히, 아니면 기존 catch-all 과 **똑같이** ERROR + 500 |
| 로그 | **DEBUG 한 줄, 스택트레이스 없이**(예외 타입·메시지는 남긴다). 필요하면 TRACE 에서만 스택 |
| 응답 | **아무것도 쓰지 않는다** — 핸들러는 `null` 을 반환한다(`HttpEntityMethodProcessor` 가 "처리됨" 으로 끝낸다). 상태코드도 손대지 않는다 |

`DisconnectedClientHelper` 가 보는 것(스프링 6.1 기준): 예외 타입 이름이 `ClientAbortException`·`AsyncRequestNotUsableException`·
`EOFException`·`EofException`·`AbortedException` 이거나, **가장 구체적인 원인의 메시지**에 `broken pipe`·`connection reset` 이 있는 경우.
요청받은 세 가지(전용 타입 2종 + 원인 사슬의 `Connection reset by peer`/`Broken pipe`)를 정확히 덮는다.

**왜 우리 문자열 목록을 만들지 않고 프레임워크 유틸을 쓰나.**
1. **스프링 자신이 같은 판단에 쓰는 기준**이다(`ExceptionHandlerExceptionResolver`, `HttpWebHandlerAdapter`). 우리 판정이 프레임워크와 갈리면
   같은 상황이 위치에 따라 다르게 로깅된다.
2. 문자열 목록은 **컨테이너·OS·로케일마다 달라지는 문구**를 우리가 계속 따라다녀야 하는 부채다. 스프링 업그레이드가 대신 갱신해 준다.
3. 톰캣 타입(`ClientAbortException`)까지 이름으로 잡아 주므로, 메시지가 없는 단절도 놓치지 않는다.

**왜 DEBUG 인가.** 서버가 잘못한 게 없고 운영자가 할 일도 없다. WARN 으로 두면 여전히 알림이 울리고 하루 60줄이 쌓인다.
스프링의 전용 유틸도 DEBUG(한 줄)/TRACE(스택)로 남긴다 — 같은 판단이다. 단절 **횟수**가 궁금해지면 그건 로그가 아니라
접근 로그·메트릭에서 볼 일이다.

**왜 본문을 쓰지 않고, 왜 499 같은 상태코드를 만들지 않나.** 커넥션이 이미 죽었으므로 **아무도 그 응답을 받지 못한다.**
본문을 만들면 위 2차 예외만 다시 만들 뿐이고, 상태코드를 지어내면 (a) 표준에 없는 코드가 계약 문서(02 §0-2)에 들어오고
(b) 이미 커밋된 응답이라 톰캣에서는 그 setStatus 조차 무시된다. **관찰자가 없는 응답을 꾸미지 않는다.**

### 20-2. 진짜 오류를 삼키지 않는 경계

단절 처리는 "조용히 넘긴다" 이므로, 잘못 넓히면 **장애가 로그에서 사라진다.** 세 겹으로 막는다.

1. **진입 타입을 `IOException` 으로 한정한다.** 런타임 예외·프레임워크 예외는 이 핸들러에 오지 않는다.
2. **판별에 걸리지 않은 `IOException` 은 지금과 완전히 같은 처리**(ERROR + 스택 + 500 `INTERNAL_SERVER_ERROR`)를 받는다.
   디스크 읽기 실패(`Input/output error`)·파일 없음(`FileNotFoundException`)이 여기 해당한다.
3. **서비스는 자기 I/O 실패를 도메인 예외로 감싼다**(현행 코드가 이미 그렇다):
   `DownloadService.prepare` → `FileUnavailableException`(503), `EditionFileService` → `BusinessRuleException`,
   `readPageCount` → `warn` 후 `null`. 그래서 **판정용 `IOException` 이 컨트롤러 밖으로 나오는 경로는 사실상 응답 쓰기뿐**이다.

**알고 감수하는 위험 하나**: 판별 목록에 `EOFException` 이 들어 있다. 손상된 PDF 를 읽다 나는 `EOFException` 이
**컨트롤러까지 그대로 올라오면** 조용히 빈 응답이 된다. 지금은 PDFBox 호출부가 전부 자기 자리에서 잡고 있어 해당 경로가 없고,
위 3번 규칙(파일 파싱 실패는 서비스에서 감싼다)을 유지하는 한 생기지 않는다. **새 파일 읽기 코드를 쓸 때 이 규칙을 지킬 것.**

경계는 테스트로 잠갔다: `ClientDisconnectLoggingIntegrationTest` 의 `real_disk_io_failure_is_still_an_error`,
`missing_file_io_failure_is_still_an_error` (둘 다 500 + ERROR 1건 + 스택).

### 20-3. 채택하지 않은 대안

- **(a) 원래 예외를 다시 던져 프레임워크에 맡긴다.** `ExceptionHandlerExceptionResolver` 는 핸들러가 원래 예외를 되던지면
  조용히 다음 리졸버로 넘기고, `DefaultHandlerExceptionResolver` 가 `AsyncRequestNotUsableException` 을 처리한다(위 3번 줄).
  → **WARN 한 줄이 계속 남고**, "되던지면 조용해진다" 는 리졸버 내부 규약에 우리 로깅 정책을 매단다. 명시적 핸들러가 읽기 쉽다.
- **(b) 로거 레벨로 끄기**(`GlobalExceptionHandler` 를 WARN 이하로). → 같은 로거의 **진짜 500 도 함께 사라진다.** 증상만 가리는 짓.
- **(c) `HttpMessageNotWritableException` 전용 핸들러도 추가.** → 실측 2차 예외는 단절이 아니라 **컨버터 선택 실패**였고(위 인용),
  본문을 안 쓰면 애초에 발생하지 않는다. 게다가 그 예외는 우리 어드바이스가 아니라 **리졸버 안에서** 나서 핸들러가 잡지도 못한다.
  잭슨은 broken pipe 를 감싸지 않고 `IOException` 그대로 던지므로 JSON 응답의 단절도 1번 핸들러가 받는다. **불필요.**

### 20-4. 테스트 — 컨벤션 §6 안에서의 선택과 그 한계

컨벤션 §6 은 백엔드 테스트를 **컨트롤러 통합테스트**로 한정한다. 이 결정도 그 안에서 검증한다.
다만 **소켓 단절 자체는 MockMvc 로 재현할 수 없다** — `MockHttpServletResponse` 는 write 에서 실패하지 않기 때문이다.
그래서 다음과 같이 갈랐다.

- **테스트하는 것**: "단절 예외가 핸들러에 도달했을 때 무엇이 남고 무엇이 나가는가" — 진짜 `DispatcherServlet` ·
  진짜 리졸버 · 진짜 `GlobalExceptionHandler` 를 통과시키고 **응답 본문과 로그 레벨**을 본다.
  예외를 던지는 **테스트 전용 엔드포인트**(`GET /api/test-support/throw/{kind}`)를 그 테스트 컨텍스트에만 등록해 결함을 주입한다.
  던지는 예외의 타입·메시지는 8084 실측 로그에서 그대로 가져왔다.
- **테스트하지 못하는 것**: 실제로 죽은 소켓에 바이트가 안 나가는지. 이건 **수동 재현**으로 확인한다(qa 6차 결함의 절차 그대로):
  `curl -s http://localhost:8084/api/editions/947/download | head -c 2000 > /dev/null` → `server-8084.log` 에 ERROR·WARN 이 **0줄**.
- **왜 이게 억지 테스트가 아닌가**: 검증 대상이 "소켓" 이 아니라 **"그 예외가 왔을 때의 정책"** 이기 때문이다.
  정책은 코드로 표현돼 있고, 그 정책이 바뀌면 테스트가 깨진다. 반대로 소켓을 진짜로 끊는 테스트(실서버 + 원시 소켓)는
  타이밍·파일 크기에 의존해 **불안정**해서 §6 의 "순서/랜덤/시간 의존 테스트 금지" 에 정면으로 걸린다.
- 테스트 전용 컨트롤러는 **그 테스트 클래스의 중첩 `@TestConfiguration`** 안에만 있다 — 다른 컨텍스트·프로덕션에는 존재하지 않는다.

**검증**: `src/test/java/com/test/test/integration/ClientDisconnectLoggingIntegrationTest.java` (5건 — 단절 3, 경계 2).

## 21. 악기 구분을 주소에 드러내는 방식 — **경로 첫 세그먼트** (2026-09-10 senior-dev)

> 기획 `04_악기구분과_검색기준_기획서.md` §3(요구 7개)·§9 8-5, 화면정의 `08` §7 S1.
> **최종 분리 방식(별도 도메인 vs 한 사이트)은 못 박지 않는다** — 사람이 정할 일이다(기획 §9 8-5).
> 여기서 정하는 것은 **어느 쪽이 와도 싸게 가는 구조** 하나다.

### 21-1. 결정

**화면 주소는 `/{구분 슬러그}/…` 경로 접두사.** 슬러그는 영어 소문자 `piano` / `violin` / `orchestra`.

| 화면 | 주소 |
|---|---|
| 홈 | `/piano` |
| 검색 결과 | `/piano/search?q=&in=&level=&pages=&downloadable=&page=` |
| 곡 상세 | `/piano/works/:id` |
| 작곡가 목록 / 상세 | `/piano/composers` / `/piano/composers/:id` |
| 준비 중 안내 | `/violin` · `/orchestra` (그 아래 하위 경로는 **없다** → 404) |
| 관리 | `/admin/**` — **구분 밖 그대로**(기획 §3-6) |
| 옛 주소 | `/` `/search` `/works/:id` `/composers` `/composers/:id` → 같은 화면의 `/piano/…` 로 **replace 리다이렉트**(쿼리 보존) |
| 없는 구분 이름 | `/cello`, `/cello/works/3` → 찾을 수 없는 페이지(구분 바는 보이되 선택 없음, 08 §3) |

**API 주소는 바꾸지 않는다.** 구분은 `/api/…` 경로가 아니라 **쿼리 파라미터 `section`** 으로 받는다(02 §0-7).

### 21-2. 왜 경로인가 (쿼리 `?section=piano` 를 버린 이유)

| # | 근거 |
|---|---|
| 1 | **기획 §3-2 "곡·작곡가 상세도 구분 아래에 놓이고 그 아래 주소 모양은 그대로".** 경로면 `/piano/works/7` → 분리 시 `piano.…/works/7` 로 **접두사만 떼면** 되고 하위 모양이 글자 하나 안 바뀐다. 쿼리(`/works/7?section=piano`)는 분리할 때 **모든 링크에서 쿼리를 지워야** 하고, 안 지운 링크는 새 사이트에서 뜻 없는 쿼리를 달고 다닌다 |
| 2 | **기획 §3-1 "주소만 보고 구분을 안다"**(인수 조건 8-B 3). 첫 세그먼트는 사람이 가장 먼저 읽는 자리다. 쿼리는 `q`·`level`·`pages`·`page` 와 섞여 눈에 띄지 않는다 |
| 3 | **기획 §3-4 "탭은 필터가 아니라 화면 이동"**. 경로가 바뀌면 브라우저·검색엔진·공유 미리보기가 **다른 문서**로 취급한다. 쿼리는 같은 문서의 변형으로 읽힌다 — designer 가 다섯 겹으로 준 신호(08 §1-2)와 주소가 같은 말을 하게 된다 |
| 4 | **서버 비용 0.** `HomeController` catch-all 과 `SpaShellRequestMatcher` 가 이미 "API·인프라가 아닌 GET" 을 전부 SPA 셸로 넘긴다(02 §0-5). `/piano/**` 를 위해 **백엔드를 한 줄도 고치지 않는다.** 회귀 가드: `SectionRouteShellIntegrationTest` |

### 21-3. 왜 영어 소문자 슬러그인가

- **한글 경로(`/피아노`)는 공유되는 순간 `%ED%94%BC…` 로 변한다.** 주소창은 예쁘게 보여 주지만 카톡·메모장·로그에 붙는 것은 인코딩된 문자열이라 인수 조건 8-B 3("주소만 보고 안다")이 깨진다.
- **서브도메인으로 옮길 때 그대로 쓴다** — `piano.…`. 한글 도메인은 punycode(`xn--…`)라 같은 이득이 없다.
- 슬러그는 **화면 주소 전용 어휘**이고, API·DB 값은 대문자 enum(`PIANO`)이다(02 §0-4 "enum 은 대문자 문자열"). 변환은 프론트 한 곳(`lib/sections.js`).

### 21-4. 두 갈래 미래에서의 비용 (사람이 나중에 고르는 것)

| 미래 | 이 구조에서 할 일 |
|---|---|
| **(a) 구분마다 별도 도메인** | 새 도메인에서 접두사를 떼고 서빙 + 옛 주소에 **규칙 한 줄**의 301: `/{slug}/*` → `{slug}.도메인/*`. 저장된 링크가 전부 살아난다 |
| **(b) 한 사이트 유지** | **아무것도 하지 않는다** |
| (참고) 쿼리였다면 | (a)에서 링크가 통째로 깨지거나, 쿼리를 읽어 도메인으로 넘기는 리다이렉터를 따로 만들어야 한다 |

### 21-5. API 에 구분 경로를 만들지 않는 이유

- **백엔드는 나뉘지 않는다.** 화면 도메인이 갈려도 API 서버를 두 벌 만들 계획이 없다(관리 화면이 구분을 넘나들며 한 벌인 것과 같은 이유 — 기획 §3-6).
- `/api/piano/works/search` 로 만들면 구분이 늘 때마다 컨트롤러 매핑이 늘고, **구분 밖인 관리 API 와 대칭이 깨진다.**
- 서버가 하는 일의 실체는 **조회 조건 하나가 늘어난 것**이다. 그 자리는 쿼리다(`level`·`pages` 와 같은 자리).

### 21-6. 현재 구분을 "기억"하지 않는다 — 화면 구현 계약

기획 §1-4 가 못 박았다: 쿠키·세션·`localStorage` 어디에도 구분을 저장하지 않는다. 같은 주소가 사람마다 다른 화면을 보이면 링크 공유가 성립하지 않는다.

- **현재 구분의 유일한 근원은 주소다.** 프론트는 `useSection()`(경로 첫 세그먼트를 읽는 훅) 하나로 답하고, 곡 카드·작곡가 카드 같은 하위 컴포넌트에 **prop 으로 내려보내지 않는다** — 내려보내는 순간 어느 호출부에서 빠뜨리면 그 링크만 구분 밖으로 나간다.
- 검색 기준(`in`)도 같은 이유로 저장하지 않는다(기획 §4-5).

### 21-7. 브라우저 탭 제목 — 라이브러리를 도입하지 않는다

화면정의 08 §5(D5)가 문자열을 확정했고, 갱신 수단은 senior-dev 몫이다.

- **`react-helmet`(-async) 류를 넣지 않는다.** 그 도구는 SSR·중첩 head 태그·meta 병합을 위한 것인데, 우리는 CSR 전용이고(CLAUDE.md) 화면마다 필요한 것은 **문자열 하나**다. 의존성 하나를 늘려 해결할 문제가 아니다.
- **`useDocumentTitle(title)` 훅 하나**(`useEffect` 로 `document.title` 대입, 언마운트 시 기본값 복귀 없음 — 다음 화면이 곧바로 자기 제목을 쓴다). 화면 컴포넌트가 호출한다.
- 계약 검증: `App.documentTitle.test.jsx`.

## 22. "이 곡을 즐겨찾기하려 했다" 를 로그인 왕복 너머로 들고 가는 수단 (2026-09-20 senior-dev)

기획 05 §1-2 가 요구한 것은 셋이다. **⑴ 돌아왔을 때 이미 켜져 있다 ⑵ 새로고침에 두 번 실행되지 않는다 ⑶ 돌아가기·뒤로 가기로는 실행되지 않는다**(인수 조건 8-B 3·4·6). 그리고 **카카오·구글 왕복에서도 같아야 한다**(8-B 5).

### 22-1. 먼저 확인한 사실 — 소셜 로그인은 `redirect` 를 잃는다

`OAuth2LoginSuccessHandler.onAuthenticationSuccess` 는 쿠키를 심은 뒤 **`sendRedirect("/")`** 한다(코드 확인, 2026-09-20). 카카오·구글은 브라우저가 우리 오리진을 **떠났다가 새 문서로 돌아오는** 흐름이라, 로그인 화면의 `?redirect=` 는 그 왕복에서 **사라진다**. 즉 주소에만 의도를 담으면 아이디·비밀번호 로그인에서는 되고 소셜에서는 안 된다 — 한 기능이 로그인 수단에 따라 다르게 동작하는 것은 결함이다.

- **그렇다고 `OAuth2LoginSuccessHandler` 를 고치지 않는다.** 소셜 로그인의 로컬 동작 정비는 사용자 작업 ④(기획 05 §0-3)이고, `application.yml` 의 redirect-uri 가 지금 손대지 말아야 할 미커밋 변경이다. **백엔드를 건드리지 않고 되는 방법이 있으면 그쪽이 맞다.**

### 22-2. 결정 — `sessionStorage` 한 칸 (`sheetmusic.loginIntent`)

```jsonc
// sessionStorage["sheetmusic.loginIntent"]
{ "action": "FAVORITE" | null, "workId": 21 | null, "returnTo": "/piano/works/21", "at": 1789... }
```

| 규칙 | 내용 |
|---|---|
| 저장소 | **`sessionStorage`** — 탭 안에서 살고, **다른 오리진(카카오·구글)에 갔다 와도 남으며**, 탭을 닫으면 사라진다. `localStorage` 는 공용 컴퓨터에서 몇 시간 뒤 다른 사람의 탭에서 되살아날 수 있어 쓰지 않는다 |
| 쓰는 곳 | ⑴ 곡 상세에서 **비로그인·세션 풀림 상태로 즐겨찾기를 눌렀을 때** → `{action:"FAVORITE", workId, returnTo: 지금 주소}` ⑵ **비로그인이 내 악보로 들어왔을 때** → `{action:null, workId:null, returnTo: 들어오려던 탭 주소}`. 둘 다 곧바로 `/login?redirect=…&reason=…`(02 §10-4)로 간다 |
| **소비 = take** | 읽는 즉시 **지운다.** 요청을 보내기 **전에** 지우는 것이 핵심이다 — 그래야 새로고침에 소비할 것이 남지 않는다(⑵) |
| 누가 소비하나 | **그 곡의 곡 상세 하나뿐.** `action === "FAVORITE" && workId === 이 곡` 일 때만. 다른 화면은 `returnTo` 만 본다 |
| 인증 확정 전에는 아무것도 하지 않는다 | `status === "loading"` 동안 소비 금지(8-B 7 — 로그인한 사람을 로딩 때문에 로그인 화면으로 보내지 않는다) |
| 비로그인으로 그 곡에 도착하면 | **take 만 하고 아무것도 하지 않는다.** 이것이 ⑶ 이다 — 로그인 화면에서 "이전 페이지로 돌아가기"·뒤로 가기로 온 경우가 정확히 이 상태이고, 의도는 그 자리에서 버려진다(안내 없음) |
| 만료 | **10분.** 지난 값은 소비하지 않고 버린다. 탭을 며칠 열어 둔 사람이 엉뚱한 순간에 즐겨찾기되는 일을 막는다 |
| `returnTo` 점프 | **앱이 뜬 뒤 인증이 확정된 첫 순간 한 번만** — 의도가 있고 만료 전이며 지금 주소가 `returnTo` 와 다르면 그 주소로 `navigate(replace)`. **소셜 왕복(`/` 로 떨어진 경우)만을 위한 한 줄**이고, 아이디·비밀번호 로그인은 `LoginPage` 가 이미 `redirect` 로 보내므로 no-op 다. 점프는 **주소만** 옮긴다 — 즐겨찾기 실행은 곡 상세가 한다(두 곳에서 실행하지 않는다) |

### 22-3. 왜 이것이 "두 번 실행"에 이중으로 안전한가

계약 쪽에서 **켜기가 멱등한 `PUT`**(02 §10-1)이다. 화면의 take 가 중복을 막고, 설령 뚫려 두 번 불려도 **결과가 같다**. 토글 API 였다면 두 번째 호출이 즐겨찾기를 **꺼서** 인수 조건 8-B 4 가 깨진다 — 계약과 화면이 같은 것을 서로 다른 방식으로 지키게 두는 것이 설계다.

- 복귀 토스트(`즐겨찾기에 넣었어요`)도 **소비한 쪽만** 띄우므로 자동으로 한 번이다. "이미 다른 기기에서 넣어 둔 곡" 과 문구를 가르지 않기로 한 결정(화면정의 09 §6 P2) 덕분에 응답에 "새로 넣었는지" 필드가 필요 없다.
- 계약 검증: `loginIntent.test.js`(take·만료·형식), `WorkDetailPage.favorite.test.jsx`(복귀 완성 한 번·새로고침 중복 금지·뒤로 가기 미실행), `Layout.loginIntentReturn.test.jsx`(소셜 왕복 점프).

## 23. 최근 본 곡은 브라우저에 **id 만** 저장한다 (2026-09-20 senior-dev)

기획 05 §4-2 의 요구: 10곡 · 구분별 · **곡 상세가 정상으로 열렸을 때만** · 보이는 정보는 **지금의 것** · 내려간 곡은 보이지 않음 · 저장이 막힌 환경에서는 **조용히 없음**.

| 항목 | 결정 |
|---|---|
| 저장소 | **`localStorage`** 키 `sheetmusic.recentWorks`. 브라우저를 닫아도 남고 **로그아웃해도 남아야** 한다(인수 조건 8-E 5) — `sessionStorage` 면 탭을 닫는 순간 사라져 규칙에 어긋난다. 시크릿 창은 저장소 자체가 달라 **아무것도 하지 않아도 빈 상태**가 된다(8-E 2·10) |
| 형태 | `{"PIANO":[23,21,22],"VIOLIN":[…]}` — **구분별 배열, 최신이 앞**(기획 05 §5-6). 곡 **id 만** 담는다 |
| 왜 id 만 | 제목·뱃지를 함께 저장하면 화면이 **저장한 순간의 정보**를 그린다. 관리자가 제목을 고치거나 준비 중이던 곡이 열려도 옛 정보가 남고, 숨긴 곡을 눌러 404 를 만난다(8-E 7·8). 그래서 표시는 매번 `GET /api/works/recent`(02 §3-9)로 지금 값을 받는다 |
| 언제 쓰나 | **곡 상세가 정상으로 그려진 뒤**(응답 200). 404·불러오기 실패·숨김 곡은 쓰지 않는다(8-E 9). 이미 있으면 **맨 앞으로 올리고 중복을 만들지 않는다**(8-E 3) |
| 상한 | **10.** 넘치면 뒤에서 버린다(8-E 4) |
| 지우기 | **지금 구분만** 비운다. 다른 구분의 목록은 그대로다(구분별 화면이므로 지금 보고 있는 목록만 사라져야 한다) |
| 저장 실패 | `try/catch` 로 **전부 삼킨다**(사파리 프라이빗·저장 차단·용량 초과). 읽기가 실패하면 빈 배열이라 영역 자체가 없다 — 오류 문구를 만들지 않는다(기획 05 §4-2 마지막 줄) |
| 값이 깨졌을 때 | JSON 파싱 실패·배열이 아님·숫자가 아닌 원소는 **무시**한다(빈 배열로 취급). 서버도 이상한 id 를 조용히 거른다(02 §3-9) |
| 구분 기억 금지와의 관계 | 기억하는 것은 **"어떤 곡을 봤나"** 이지 "지금 어느 구분인가" 가 아니다(기획 05 §4-4). `useSection()` 규칙(§21-6)과 충돌하지 않는다 |

- 구현 자리: `frontend/src/lib/recentWorks.js`(읽기·기록·비우기 세 함수). 화면은 이 파일만 부른다 — `localStorage` 를 여러 화면이 직접 만지면 키·형태가 곧 갈린다.
- 계약 검증: `recentWorks.test.js`, `HomePage.recentWorks.test.jsx`, `WorkDetailPage.favorite.test.jsx`(정상으로 열렸을 때만 기록).

## 24. 받은 악보는 `download_log` 위에 얹지 않고 **별도 원장**으로 둔다 (2026-09-20 senior-dev)

기획 05 §11 ④ 는 "다운로드 기록에 **누가** 를 붙이라" 고 했다. 가장 짧은 답은 `download_log.user_id` 한 컬럼이지만, 그 위에 받은 악보 화면을 세우면 **읽기 질의가 곡 단위 최신 1행 뽑기(greatest-n-per-group)** 가 된다 — 정렬·페이지·판본 조인이 전부 그 위에 얹힌다.

**결정: `download_log` 는 한 글자도 바꾸지 않고, `user_work_download`(01_ERD §3-12)를 새로 둔다.**

| 이유 | 내용 |
|---|---|
| 집계를 흔들지 않는다 | `download_log` 는 인기곡 정렬과 대시보드 `monthlyDownloads` 의 원장이다(§17·02 §4-1, qa 3차 결함 8 로 어렵게 정리한 자리). **비로그인 다운로드도 계속 기록된다**(인수 조건 8-D 3)는 회귀를, 그 표를 건드리지 않는 것으로 **구조적으로** 보장한다 |
| 화면이 요구한 모양 그대로다 | 받은 악보는 "곡 단위 한 줄" 이다(기획 05 §3-2). 그러면 **행 하나가 곧 화면 한 줄**이라 정렬(`last_downloaded_at DESC`)·페이지·숫자가 인덱스 하나로 끝난다 |
| 판본 설명을 남길 자리가 생긴다 | 삭제된 판본의 설명을 **한 줄에 하나만** 스냅샷하면 된다. `download_log` 에 붙이면 같은 값이 다운로드 횟수만큼 복제된다 |
| 소급이 없다는 사실이 눈에 보인다 | 새 표는 비어서 시작한다 — "기능 도입 전 기록은 누구의 것도 아니다"(8-D 4)가 마이그레이션 없이 그냥 참이 된다 |

- 대가: 다운로드 1건에 쓰기가 2번(로그 INSERT + upsert)이다. 같은 짧은 트랜잭션 안이고 둘 다 인덱스 한 방이라 받아들인다. **읽기 쪽 복잡도를 쓰기 한 번으로 바꾼 거래**다.
- 그래서 "누가 뭘 받았나" 를 **관리자도 볼 수 없다**(기획 05 §3-1) — 그 표를 읽는 API 가 `/api/me/library/downloads` 하나뿐이고, 그 문은 토큰 주체로만 연다(02 §10-0).
- 계약 검증: `MyLibraryDownloadApiIntegrationTest`(비로그인 다운로드가 계속 집계에 들고 받은 악보에는 안 남는 회귀 포함).

## 25. 알고 있으나 지금은 미루는 것 네 가지 (2026-09-21 senior-dev, 즐겨찾기·받은 악보 코드리뷰)

§19-1 과 같은 자리다 — **고치지 않기로 한 것이 아니라, 지금 고치지 않기로 한 것**과 그 방아쇠를 적어 둔다.
(25-4 는 이번 기능이 만든 것이 아니라 같은 코드리뷰 중 대조하다 찾은 **기존** 결함이다 — 항목 안에 따로 적어 둔다.)

### 25-1. Toast 의 성공·실패 아이콘과 수동 닫기 (00 §3-11)

화면 정의서는 Toast 에 `check_circle`(성공)·`error`(실패) 아이콘과 수동 닫기 `close` 를 요구하는데 `Toast.jsx` 에는 셋 다 없다.

- **이번 라운드의 누락이 아니다.** 그 문장은 관리 화면 Toast 시절부터 있었고(2026-09-20 개정 diff 에 없다), 이번에 새로 어긋난 것은 없다. 반대로 이번에 추가된 **되돌리기 변형은 "아이콘 없음"이 명시**라 이 기능이 요구하는 것도 아니다.
- **지금 붙이면 이 기능과 무관한 관리 화면 Toast 10여 곳의 모양이 같은 변경에 섞인다.** 회원 기능 변경과 전역 UI 변경이 한 덩어리가 되면 qa 가 무엇을 보고 판정해야 하는지가 흐려진다.
- frontend-dev 가 든 "문구 단언이 깨진다" 는 근거는 **과대평가**다(실측: `role="status"` 를 읽는 테스트 2곳뿐이고 둘 다 부분 문자열 비교라 통과한다). 그래도 미루는 이유는 위의 둘이다 — **테스트 비용이 아니라 변경 묶음의 크기** 때문이다.
- **방아쇠**: Toast 를 손대는 다음 작업. 그때 아이콘 2종 + `close` 를 한 번에 붙이고 `Toast.test.jsx` 에 아이콘·닫기 테스트를 더한다. 닫기 버튼의 접근 이름은 `닫기` 가 이미 라이트박스에 있으므로(`WorkDetailPage.test.jsx`) **`알림 닫기`** 로 둬야 조회가 모호해지지 않는다.
- **해제 (2026-09-21)** — 이 라운드가 Toast 만 손대는 작업이라 방아쇠가 당겨졌다. 계약은 **§29**, Red 는 `Toast.variants.test.jsx` · `FavoriteToastVariant.test.jsx`.

### 25-2. 다운로드 진행 표시 — 스피너·`disabled`·10초 자동 복귀 (03 §251, 09 §1-2-1)

곡 상세도 받은 악보도 지금은 글자만 `받는 중…` 으로 바꾼다. 스피너·`disabled`·10초 자동 복귀는 **두 화면 모두** 없다.

- 받은 악보가 곡 상세와 **같은 수준**으로 맞춘 것은 옳다(한 제품 안에서 같은 동작이 화면마다 다르게 보이는 쪽이 더 나쁘다).
- **한 곳만 고칠 수 없는 일이다.** 고친다면 "다운로드 시작 표시" 를 공용 훅 하나로 만들어 두 화면에 함께 걸어야 하고, 그러면 이미 qa 를 통과한 곡 상세를 이 라운드에서 다시 건드리게 된다.
- **방아쇠**: 다음 라운드 첫 항목으로 senior-dev 가 훅 계약과 테스트(진행 중 `disabled`·10초 뒤 복귀)를 먼저 쓰고 frontend-dev 가 두 화면에 함께 적용한다. 그 전까지 09 §1-2-1 "진행 중" 행과 03 §251 은 **미구현 상태로 알려진 것**이다.
- **해제 (2026-09-21)** — 계약은 **§28**(`useDownloadStart`), Red 는 `useDownloadStart.test.jsx` · `WorkDetailPage.downloadProgress.test.jsx` · `MyLibraryPage.downloadProgress.test.jsx`. 구현은 frontend-dev 가 **두 화면에 한 번에** 한다.

### 25-3. Hibernate 가 VARCHAR enum 컬럼에 붙이는 `CHECK` 제약 (01_ERD §9-1 의 뒷면)

§9-1 로 네이티브 `enum(...)` 은 없앴지만, Hibernate 6 은 `@Enumerated(STRING)` 컬럼에 `check (c in ('A','B'))` 를 함께 만든다. 그래서 **기존 DB 에 enum 상수를 더하면** 새 값이 옛 제약에 걸려 INSERT 가 실패한다(`ddl-auto: update` 는 제약을 다시 만들지 않는다).

- **이번 기능의 문제가 아니다.** `user_work_download` 의 스냅샷 2개(`edition_kind`·`edition_scope`)는 기존 enum 을 그대로 쓰고 값을 더하지 않는다. 16개 컬럼 전부에 해당하는 **프로젝트 전체의 성질**이다.
- **지금 손대지 않는다.** 없애려면 `hibernate.hbm2ddl.schema_filter` 나 `@Check` 를 끄는 전역 설정, 또는 DDL 을 Hibernate 에서 떼어내는(Flyway) 결정이 필요한데, 그건 §17(로컬 파일 H2)·§9 대장 운영 방식 전체를 바꾸는 일이라 기능 라운드에 끼워 넣을 크기가 아니다.
- **방아쇠**: enum 상수를 **실제로 추가하는** 첫 순간. 그때 §9 대장에 `ALTER TABLE t DROP CONSTRAINT <check 이름>` 한 줄을 함께 적는다(H2·MySQL 모두 제약 이름은 생성 DDL 로 확인한다). 운영 DB 가 생기기 전이면 재생성이 더 싸다.
- 회귀 가드 `SchemaEnumColumnTypeIntegrationTest` 는 **타입만** 본다 — 제약까지 보게 넓히지 않는다(지금은 제약이 있는 것이 정상이므로 가드가 거짓 경보가 된다).

### 25-4. `DownloadMetaReader.read` 의 클래스 트랜잭션이 실제로는 안 열린다 (기존 결함, 2026-09-21 코드리뷰 중 발견)

`DownloadMetaReader`(02 §3-4, 본 문서 §4)는 클래스에 `@Transactional(readOnly = true)`를 걸고, `read(Long)` 하나로
"판본 조회 → 숨김 곡 404 → 파일 없음 404 → 저작권 403 → files 조회"를 **한 번의 짧은 읽기 트랜잭션**으로 묶는다고
클래스 javadoc에 적어 뒀다. 그런데 `read`가 **package-private**이다. Spring 의 프록시 기반 트랜잭션은
`AnnotationTransactionAttributeSource`가 기본값 `publicMethodsOnly=true`로 **public 메서드만** advice 대상으로 삼는다
(클래스 레벨 애너테이션이 있어도 non-public 메서드는 대상에서 빠진다 — Spring 공식 문서에 명시된 동작). 그래서 실제로는
`read()` 전체를 감싸는 트랜잭션이 **열리지 않고**, 안에서 부르는 `editionRepository.findById`·`fileRepository.findById` 가
**Spring Data 저장소 자신의 `@Transactional(readOnly=true)`**(`SimpleJpaRepository` 클래스 레벨)로 **호출마다 각자**
독립된 짧은 트랜잭션을 열고 닫는다 — javadoc 이 약속하는 "트랜잭션 하나"가 아니라 "리포지토리 호출 수만큼"이다.

- **이번 기능(즐겨찾기)의 결함이 아니다.** `DownloadMetaReader`는 이번 라운드에서 손대지 않았다 — `FavoriteService`의
  트랜잭션 예외(컨벤션 스킬 §1)를 코드리뷰하며 같은 "클래스 트랜잭션 + 짧은 트랜잭션 분리" 패턴을 대조하던 중 발견했다.
- **지금 증상이 없는 이유.** 이 경로는 쓰기가 없는 순수 조회이고, `PublicReadApiWithoutTestTransactionIntegrationTest`의
  `download_worksWithoutOpenSession`·`downloadLibrary_worksWithoutOpenSession`이 **테스트 트랜잭션 없이**
  (`NonTransactionalApiTestSupport`, §14) 이 경로를 실제 HTTP 요청으로 통과시켜 초록이다 — 지금 조합에서 이 분할이
  눈에 보이는 오류(500·값 불일치)를 만들지 않는다는 뜻이다. 다만 이건 **javadoc 이 약속하는 원자성이 실제로 검증된
  것이 아니라, 지금은 그 틈이 드러나지 않고 있을 뿐**이다 — 계약이 아니라 우연히 버티는 상태라, Hibernate 버전이나
  연관관계 fetch 전략이 바뀌면 조용히 깨질 수 있다.
- **이번 라운드에서 고치지 않는다.** 지금은 빌드 중이라 코드를 건드릴 수 없고, 컨벤션 §6("테스트 → 코드" 순서)상
  고치기 전에 이 경계 — "여러 리포지토리 호출이 정말 한 트랜잭션 안에서 도는가" — 를 관찰할 수 있는 테스트부터
  있어야 한다. 지금 두 통합테스트는 "최종 결과가 맞는지"만 보지 "트랜잭션이 하나인지"는 보지 않아서, 이 결함을
  검출하지 못한다(그래서 지금까지 안 잡혔다).
- **고칠 때 필요한 것.** ① 트랜잭션 경계를 관찰하는 테스트를 먼저 쓴다(예: 두 리포지토리 호출 사이에서
  `TransactionSynchronizationManager.isActualTransactionActive()`/트랜잭션 이름을 로그로 남겨 같은 트랜잭션인지 확인,
  또는 조회 도중 다른 트랜잭션이 파일 행을 지우는 경합을 재현). ② 그 테스트가 Red 임을 확인한 뒤 `read`의
  접근제어자를 `public`으로 바꾼다 — 로직은 그대로이고 수정 자체는 한 줄이다.
- **방아쇠.** (a) 이 클래스(또는 이 경로)에 **쓰기**가 생기는 순간(예: 다운로드 준비 중 상태 갱신) — 쓰기가 섞이면
  "안 열리는 트랜잭션"은 곧 원자성 결함이 된다. (b) 여러 리포지토리 호출 사이의 **원자성이 실제로 요구되는 기능**이
  생기는 순간(예: 조회 도중 판본이 삭제되거나 저작권 판정이 바뀌면 안 되는 요구). (c) 코드리뷰에서 **같은 함정**
  (클래스 레벨 트랜잭션 + package-private 진입 메서드)이 다른 곳에서 또 발견되는 순간 — 그때는 개별 수정이 아니라
  `code-convention` 스킬에 "트랜잭션이 걸린 클래스의 진입 메서드는 public이어야 한다"는 규칙 추가를 함께 검토한다.

## 26. 받은 악보 upsert 의 경합 — 제약 위반을 "처리" 하지 말고 **일어나지 않게** 한다 (2026-09-21 senior-dev, qa 8차 결함 1)

같은 계정이 **한 번도 안 받은 곡**을 같은 순간에 두 번 받으면 `GET /api/editions/{id}/download` 가 `200, 500` 을 낸다(qa 실측 3/3, 4발이면 `500,200,200,500`). `MyLibraryRecorder.recordDownload` 의 `findByUserIdAndWorkId(...).ifPresentOrElse(수정, save)` 가 "있나 보고 없으면 넣는다" 라서, 두 요청이 같은 창에 들어오면 뒤에 온 쪽이 `uk_user_work_download` 를 위반한다. **위험 창은 생각보다 넓다** — 카운터 증가는 dirty checking 이라 커밋까지 flush 되지 않아 판본 행 잠금이 요청을 직렬화해 주지 않고, 큰 PDF 를 나란히 읽으면 "바이트 확보 → 기록" 시점이 겹친다.

**진짜 피해는 500 자체가 아니라 그 500 이 끌고 간 것**이다: `recordDownload` 는 한 트랜잭션이라 제약 위반이 **집계(`download_log` 1행 + 두 `download_count`)까지 통째로 롤백**한다. 그 사람은 파일을 실제로 받아 갔는데 원장에는 안 받은 것이 된다.

### 26-1. 즐겨찾기(§FavoriteWriter) 방식을 그대로 옮기지 않는 이유

`FavoriteService` + `FavoriteWriter`(컨벤션 §1 예외 ②)는 **호출자가 트랜잭션 밖**이라 성립한 구조다. 여기는 **다운로드 본체 트랜잭션 안**이라 같은 모양이 되려면 `REQUIRES_NEW` 여야 하는데, 그 순간 성질이 셋 달라진다.

| # | REQUIRES_NEW 로 옮기면 생기는 것 |
|---|---|
| ① | **커밋이 둘로 갈린다.** 선반이 먼저 커밋되고 집계가 나중이라 §24·01_ERD §3-12 가 약속한 "집계와 선반은 같은 트랜잭션" 이 깨진다 |
| ② | **자기 자신을 기다릴 수 있다.** 안쪽 트랜잭션은 **다른 커넥션**인데, 넣으려는 행의 FK 부모(`users`·`work`·`edition`)를 바깥 트랜잭션이 이미 잠갔으면(카운터 UPDATE 가 flush 된 뒤) 안쪽이 바깥의 잠금을 기다린다 — 같은 요청 안에서의 잠금 대기라 타임아웃까지 아무도 풀어 주지 않는다(MySQL InnoDB 의 FK 부모 공유잠금) |
| ③ | **위반 뒤 다시 읽어도 안 보일 수 있다.** MySQL 기본 격리수준(REPEATABLE READ)에서 바깥 트랜잭션의 스냅샷은 시작 시점에 고정되므로, 겹친 요청이 방금 커밋한 행이 일반 SELECT 에 안 나타난다 → "없네" 하고 또 INSERT → 또 위반 |

### 26-2. 결정 — **넣기를 DB 단일 문장으로** (`INSERT … ON DUPLICATE KEY UPDATE`)

읽고-나서-**넣는** 창 자체를 없앤다. 한 문장이면 중간에 낄 자리가 없어 제약 위반이 발생하지 않고, 본체 트랜잭션은 그대로 하나로 남는다(커밋 1회·커넥션 1개·집계와 선반이 함께 커밋).

- **조회(`findByUserIdAndWorkId`)와 "있으면 수정" 경로는 그대로 둔다.** 위험한 갈래는 **처음 받는 곡** 하나뿐이다 — 줄이 이미 있으면 그 행의 잠금이 동시 요청을 줄 세우므로 제약을 위반할 길이 없고, 흔한 길(다시 받기)은 JPA 의 dirty checking 그대로 두는 것이 읽기 쉽다. 바꾸는 것은 **`save(new …)` 한 줄 → upsert 한 문장**이다.
- 이 선택은 **회귀 가드를 살려 두기도 한다**: 경합 테스트는 "조회가 한 번 거짓말한다" 로 그 순간을 고정하므로(§26-3), 조회를 없애면 다시 `save` 로 되돌아가는 회귀를 잡을 자리가 사라진다.

- **환경 확인 완료**(senior-dev 실측): H2 2.2.224 · 2.3.232 모두 `MODE=MySQL` 에서 `ON DUPLICATE KEY UPDATE` 를 지원한다. 우리 세 환경이 전부 그 문법 위에 있다 — 테스트 `jdbc:h2:mem:…;MODE=MySQL`, 로컬 dev `jdbc:h2:file:./data/devdb;MODE=MySQL`, 운영 Railway MySQL.
- **`VALUES(col)` 같은 MySQL 전용 함수를 쓰지 않는다** — 갱신할 값도 **파라미터로 다시 넘긴다**(두 DB 에서 문법이 같아진다).
- **스냅샷 5개의 계산은 엔티티에 남긴다.** `UserWorkDownloadEntity` 가 판본에서 뽑던 값(`kind·scope·movementNumber·pageCount·fileSize`)을 SQL 이 다시 계산하면 규칙이 두 곳이 된다. upsert 파라미터는 **엔티티가 계산한 값**을 그대로 넘긴다.
- **§17-5(스키마 드리프트)에 딸린 의무**: `user_work_download` 의 컬럼을 바꾸면 이 네이티브 문장도 같이 고친다. 네이티브 SQL 은 컴파일 타임에 안 걸린다 — 이 표에 컬럼을 더하는 사람이 보게 01_ERD §3-12 에도 한 줄 남긴다.
- 대가: **처음 받는 곡 한 갈래**에서 JPA 대신 우리가 문장을 쓴다. **경합을 "처리" 하는 코드(재시도·재조회·예외 분기)가 통째로 없어지는 값**으로 받아들인다 — 처리 경로는 테스트가 닿기 어렵고, 닿지 않은 예외 경로는 결국 운영에서 처음 실행된다.
- `created_at` 은 **INSERT 에서만** 쓴다(그 사람이 이 곡을 처음 받은 시각 — 01_ERD §3-12). `ON DUPLICATE KEY UPDATE` 목록에 넣으면 "처음" 이 매번 갱신돼 거짓이 된다. 값은 그 다운로드 시각이고, **그 규칙은 엔티티 생성자에만 둔다**(§26-4).
- 계약: 02 §3-4(겹친 요청도 둘 다 200) · §10-3. 검증: `MyLibraryDownloadRaceIntegrationTest`.

### 26-3. 규칙 — **"있나 보고 넣는" 자리에는 경합 테스트를 짝으로 둔다** (qa 8차 지적)

qa 가 남긴 지적은 결함 하나가 아니라 **빈자리**였다: 같은 위험이 두 곳에 있었는데 테스트는 한 곳에만 있었다.

| 표 (unique 제약) | 쓰는 곳 | 경합을 막는 방식 | 경합 테스트 |
|---|---|---|---|
| `work_favorite` (`uk_work_favorite`) | `FavoriteService.turnOn` → `FavoriteWriter.insertIfAbsent` | 별도 트랜잭션 + 위반을 트랜잭션 밖에서 받아 "이미 켜짐" 확인 (컨벤션 §1 예외 ②) | `FavoriteTurnOnRaceIntegrationTest` |
| `user_work_download` (`uk_user_work_download`) | `MyLibraryRecorder.recordDownload` | **넣기를 DB 단일 문장 upsert 로**(§26-2) — 본체 트랜잭션 안이라 분리할 수 없다 | `MyLibraryDownloadRaceIntegrationTest` |

- **규칙**: unique 제약 위에서 "조회 → 없으면 삽입" 을 하는 코드를 새로 쓰면, ① 위 표에서 방식을 고르고(호출자가 트랜잭션 밖이면 분리, 안이면 upsert) ② **결정적 경합 테스트를 같은 커밋에 둔다** ③ 이 표에 줄을 더한다. 표가 곧 점검 목록이라, 다음 사람이 "여긴 왜 없지" 를 한눈에 본다.
- **테스트 방식은 스레드가 아니라 스텁이다**(컨벤션 §6 "순서/랜덤 의존 테스트 금지"): "있나" 를 **한 번만** 거짓으로 답하게 해 그 순간을 고정하고, 그 뒤의 물음은 실제 DB 를 본다. 스레드 경합은 뜨는 날·안 뜨는 날이 갈려 회귀 가드가 되지 못한다.
- **테스트 트랜잭션이 없어야 한다**(`NonTransactionalApiTestSupport`): 제약 위반은 트랜잭션을 rollback-only 로 만들므로, 테스트가 트랜잭션을 열어 둔 채 돌면 운영에서 벌어지는 일을 볼 수 없다.
- 컨벤션 스킬 §6 에도 같은 한 줄을 넣었다(테스트 방침은 그 문서가 기준이므로).

### 26-4. `created_at` 규칙은 **엔티티 생성자 한 곳**에 둔다 — `@PrePersist` 는 지운다 (2026-09-21 senior-dev 코드리뷰, backend-dev 제기)

upsert 가 이 표의 **유일한 삽입 경로**가 되면서 `UserWorkDownloadEntity.@PrePersist` 는 **실행되지 않는 코드**가 됐다(남은 호출자 없음). 그대로 두면 "처음 받은 시각" 의 규칙이 둘이 된다 — 네이티브 문장은 **다운로드 시각**, `@PrePersist` 는 **flush 시각(`Instant.now()`)**. 지금은 뜻이 같지만, 나중에 누가 `save(new UserWorkDownloadEntity(...))` 를 다시 쓰는 순간 경로마다 값이 갈린다.

- **결정**: `@PrePersist` 를 지우고 `created_at` 을 **생성자**에서 `downloadedAt` 으로 채운다. `MyLibraryRecorder` 는 나머지 9개와 똑같이 `row.getCreatedAt()` 을 넘긴다 — 그러면 **upsert 파라미터 10개가 전부 엔티티가 계산한 값**이 돼 §26-2 의 "계산은 엔티티에 남긴다" 가 예외 없이 성립하고, 누가 `save()` 로 되돌아가도 같은 값이 들어간다.
- **왜 그냥 지우기(생성자도 안 채우기)가 아닌가**: `created_at` 은 NOT NULL 이라 `save()` 가 터지긴 한다. 하지만 그 실패는 **운영에서 처음** 보게 된다 — 생성자가 채우면 되돌아간 경로도 *맞는 값*을 쓴다.
- **왜 javadoc/컨벤션 한 줄로 끝내지 않는가**: 규칙이 두 곳에 있는 한, 글로 적은 약속은 다음 사람이 읽지 않으면 그만이다. 한 곳으로 합치면 읽지 않아도 어긋날 수 없다.
- **가드**(구현과 같은 커밋): `MyLibraryDownloadRaceIntegrationTest` — 겹친 요청(= upsert 의 **갱신** 절반)이 지나가도 `created_at` 은 그대로이고 `last_downloaded_at` 만 움직인다. `MyLibraryDownloadApiIntegrationTest.createdAtIsTheDownloadTime` — 첫 줄에서 두 값이 같고, 시계 창(±60초) 안이다(시간대가 밀린 값·0 을 잡는다). 갱신 목록에 `created_at` 을 넣어 보면 race 테스트가 Red 가 되는 것까지 확인했다.

## 27. 문자열 `@Query` 로 페이지를 읽으면 offset 이 `int` 로 좁혀진다 (2026-09-21 senior-dev, qa 8차 결함 2)

`GET /api/me/library/favorites?page=2147483647`(그리고 `/downloads`)이 500 이었다 — `InvalidDataAccessApiUsageException: Page offset exceeds Integer.MAX_VALUE`. 경계는 `page=107374182` 200 / `107374183` 부터 500 (= `size` 20 기준 offset 이 `Integer.MAX_VALUE` 를 넘는 첫 페이지). 같은 값으로 `/api/works/search`·`/api/composers/{id}/works`·`/api/admin/works` 는 전부 200 이다: 스프링 데이터가 **문자열 `@Query`** 로 만든 질의에만 `PageableUtils.getOffsetAsInteger` 를 태우기 때문이고, 내 악보 두 탭만 그 방식이다.

**결정: 범위 밖 페이지는 애초에 질의하지 않는다.** `MyLibraryQueryService` 가 이미 세는 값(`counts`)이 그 탭의 총 개수와 **항상 같다**(02 §10-2)는 것을 이용해, `pageable.getOffset() >= total` 이면 질의 대신 빈 페이지(`new PageImpl<>(List.of(), 요청한 Pageable, total)`)를 만든다.

- **왜 clamp(페이지를 최대값으로 깎기)가 아닌가**: `page` 는 주소창에 그대로 드러나는 값이라 화면이 그 값을 다시 쓴다. 서버가 몰래 다른 페이지로 옮기면 "다음 페이지를 눌러도 그 자리" 가 된다. 요청한 값을 되비추고 목록만 비우는 쪽이 다른 목록 API 와도 같은 답이다(02 §0-4).
- **왜 400/404 가 아닌가**: 범위 밖 페이지는 "잘못된 요청" 이 아니라 **"그 페이지에 아무것도 없는 상태"** 이고, 화면정의 09 상태표가 이미 그 화면을 정의하고 있다. 다른 목록이 200 인데 이 둘만 400 이면 계약이 목록마다 갈린다.
- **덤**: 범위 밖 요청에서 질의 한 번이 통째로 사라진다(총 개수는 어차피 세고 있다).
- **`totalElements` 의 원천을 하나로** (2026-09-21 코드리뷰 추가 결정 — 구현은 backend-dev): 지금은 같은 수를 **두 번** 센다 — 탭 머리용 `countVisible` 과 페이지 질의에 딸린 `countQuery`. **빈 페이지 분기만** `counts` 를 쓰고, 실제로 질의하는 경로의 `totalElements` 는 `countQuery` 가 만든다. 두 JPQL 이 **글자 그대로 같아서** 계약(02 §10-2 "`counts` 는 `totalElements` 와 항상 같다")이 지켜지고 있을 뿐이라, 숨김·구분 조건을 한쪽만 고치면 **조용히** 갈린다(응답은 200 이고 숫자만 어긋난다). **결정**: 페이지 질의는 `List<E>` 로 받고(딸린 `countQuery` 는 지운다) `pageOf` 가 `new PageImpl<>(content, 요청한 Pageable, total)` 로 감싼다 — `counts` 가 **유일한 원천**이 되고, 두 분기가 같은 모양이 되며, 요청당 count 질의가 3 → 2 로 준다.
- **하지 않는 것**: 두 `@Query` 를 파생 질의·Specification 으로 바꿔 offset 을 `long` 으로 되돌리는 것. 정렬·숨김·구분 조건이 그 문자열 안에 있어 질의를 다시 쓰는 일이 되고, 정렬 계약(§10-2·§10-3)이 흔들릴 위험이 실익보다 크다.
- **알려진 채로 두는 것**: `page = Integer.MAX_VALUE` 에서 응답 `last` 가 `false` 로 온다 — 스프링 데이터 `PageImpl.hasNext()` 가 `getNumber() + 1` 로 판정해 int 가 넘치기 때문이고, **모든 목록 API 가 똑같다**(우리 코드의 문제가 아니라 프레임워크의 경계값이다). 이번에 바로잡는 것은 500 이다. 화면이 그 값을 쓰는 페이지 번호는 현실에 없다.
- 계약: 02 §0-4 · §10-2 · §10-3. 검증: `MyLibraryPageBoundsIntegrationTest`.

## 28. 다운로드 진행 표시는 **공용 훅 하나**로 — 10초는 실패 판정이 아니라 **잠금 해제 장치**다 (2026-09-21 senior-dev, §25-2 해제)

화면정의 03 §251 과 09 §1-2-1 이 요구하는 "버튼 `받는 중…` + 스피너 + `disabled` + 최대 10초 자동 복귀" 중
지금 있는 것은 **문구뿐**이다. 두 화면(곡 상세 `PDF 받기` · 내 악보 `다시 받기`)이 각자 `useState` 로 같은 일을
따로 한다 — 한 곳만 고치면 **같은 동작이 화면마다 다르게 보인다**(§25-2 가 미룬 이유).

### 28-1. 계약 — `useDownloadStart` (frontend/src/hooks/useDownloadStart.js, 구현은 frontend-dev)

```js
const download = useDownloadStart({ url, className, onSuccess });
// → { state: "idle"|"checking"|"failed", busy, failed, linkProps }
```

| 항목 | 값 |
|---|---|
| `url` | 다운로드 주소(`/api/editions/{id}/download`). 없으면 링크를 렌더하지 않는 것이 호출자 책임 |
| `className` | 버튼 기본 클래스(`"btn btn-primary btn-lg"`). 훅이 진행 중에 `is-disabled` 를 **합성해서** 돌려준다 |
| `onSuccess` | HEAD 200 일 때 **한 번** 호출(내 악보의 `오늘 받음` 갱신). 10초가 지나 도착한 응답에서는 **부르지 않는다** |
| `linkProps` | `{ href, download, onClick, className, aria-disabled }` — 그대로 `<a>` 에 펼친다 |
| 상수 | `DOWNLOADING_LABEL = "받는 중…"`, `DOWNLOAD_RELEASE_MS = 10_000` — 두 화면이 **나눠 쓰는 값**이다 |

동작 규칙(전부 `useDownloadStart.test.jsx` 가 잠근다)

1. **첫 클릭의 기본 동작은 막지 않는다.** 네이티브 다운로드가 그대로 시작돼야 한다(02 §7 — fetch 로 blob 을 받지 않는다).
2. 클릭과 동시에 `checking` + 같은 주소로 `HEAD` 한 번(§12).
3. **받는 중 재클릭은 `preventDefault()` 하고 요청을 더 보내지 않는다.** 지금은 누를 때마다 HEAD 가 늘어난다.
4. 끝 판정은 HEAD 응답이다 — 200 이면 `idle` + `onSuccess`, 4xx/5xx·네트워크 오류면 `failed`.
5. **10초가 지나면 무조건 `idle`.** 기준 시각은 **클릭(요청 시작)** 이다.
6. **10초 복귀는 실패가 아니다.** `failed` 로 가지 않고 안내도 띄우지 않는다.
7. **10초가 지나 도착한 응답은 성공이든 실패든 버린다** — 상태도 `onSuccess` 도 움직이지 않는다.
8. 받는 중에 화면이 사라지면 타이머도 함께 사라진다.

### 28-2. `<a>` 에는 `disabled` 가 없다 — 잠금은 `aria-disabled` + 재클릭 차단이다

정의서의 `disabled` 를 그대로 옮길 수 없다. 이 버튼은 `<button>` 이 아니라 `<a href download>` 이고(02 §7),
HTML 의 `disabled` 는 앵커에 없는 속성이다. 그래서 잠금을 셋으로 나눈다.

| 무엇을 | 어떻게 | 왜 |
|---|---|---|
| 보이는 잠금 | `className` 에 `is-disabled` | `.btn:disabled` 와 **같은 모양**을 공유한다(CSS 한 줄 추가) |
| 읽히는 잠금 | `aria-disabled="true"` | 앵커에 쓸 수 있는 유일한 표준 표현. 역할(`link`)은 그대로라 조회가 깨지지 않는다 |
| 실제 차단 | `onClick` 에서 `preventDefault()` + 요청 생략 | 동작으로 막는다 |

- **`href` 를 지우지 않는다.** 클릭 직후 리렌더에서 주소를 떼면 이미 시작된 네이티브 다운로드를 끊을 수 있고,
  포커스 가능한 요소가 아니게 돼 키보드 사용자가 버튼을 잃는다.
- **`pointer-events: none` 을 쓰지 않는다.** 클릭 이벤트 자체가 안 오면 우리가 막았는지 알 수 없고(테스트도 못 한다),
  키보드 Enter 는 그대로 통과해 반쪽짜리 잠금이 된다.

### 28-3. §12 가 "타이머 폴백은 필요 없다" 고 한 것과 어긋나지 않는다

§12(2026-09-07)는 **실패 감지 수단**으로서의 10초 타이머를 기각했다 — 타이머로는 실패를 *알 수 없기* 때문이고,
그 자리는 HEAD 가 가져갔다. 그 판단은 그대로 유효하다. 여기서 10초가 하는 일은 **다른 일**이다:

> `disabled` 를 붙이는 순간, 응답이 영영 오지 않는 요청 하나가 **버튼을 영구히 잠근다**.
> `fetch` 에는 기본 타임아웃이 없다. 잠금이 없던 시절에는 사용자가 그냥 다시 누르면 됐지만, 이제는 그 길이 막힌다.

그래서 10초는 **감지기가 아니라 자물쇠 해제 장치**다. 이 성질에서 규칙 6·7이 따라 나온다 —
자물쇠만 푸는 장치이므로 "실패했다" 고 말할 자격이 없고(6), 이미 손을 뗀 일에 대해 10초 뒤에 나타나
화면을 뒤에서 바꿀 자격도 없다(7). 특히 **내 악보**에서 늦게 온 200 이 날짜를 `오늘 받음` 으로 바꾸면,
사용자가 이미 다른 탭을 보고 있는 사이에 목록이 혼자 움직인다.

### 28-4. 훅이지 컴포넌트가 아닌 이유

두 화면은 **라벨이 다르고**(`PDF 받기 · 2.4MB` / `다시 받기` / `지금 추천 판본 받기`) **실패 안내의 출구가 다르다**
(곡 상세는 IMSLP 링크, 내 악보는 `곡 보기`). 게다가 내 악보의 안내는 버튼 바로 옆이 아니라 **항목 맨 아래**다(09 §1-2-2).
버튼+안내를 통째로 컴포넌트로 만들면 이 차이들이 전부 prop 이 돼 오히려 갈라진다. **규칙은 훅이 잠그고, 모양은
`.btn-spinner` 라는 클래스 하나로 두 화면 테스트가 같이 잠근다.**

- 내 악보는 목록이라 **행마다** 진행 상태가 따로다. `ReceivedRow` 가 이미 컴포넌트이고 `key={row.work.id}` 라,
  훅을 **행 컴포넌트 안에서** 부르면 페이지의 `downloadState` 맵(`{[workId]: state}`)이 통째로 사라진다 — 상태의 자리가 곧 행이 된다.
- 계약 검증: `useDownloadStart.test.jsx`(규칙 1~8) · `WorkDetailPage.downloadProgress.test.jsx` · `MyLibraryPage.downloadProgress.test.jsx`(두 화면이 같은 단언).

## 29. Toast 아이콘의 기본값은 **성공**이다 — 호출부 10여 곳을 고치지 않기 위해 (2026-09-21 senior-dev, §25-1 해제)

00 §3-11 은 Toast 에 성공 `check_circle` · 실패 `error` · 수동 닫기 `close` 를 요구하는데 셋 다 없다.
§25-1 이 미룬 이유는 "관리 화면 Toast 10여 곳의 모양이 회원 기능 변경에 섞인다" 였고, **이번 라운드는 그 제약이 없다.**

### 29-1. 시그니처 — `variant` 를 더하되 기본값이 성공이다

```js
showToast(message, { variant = "success", action, durationMs })   // "success" | "danger"
```

- **기존 호출부 `showToast("저장했어요")` 는 한 글자도 고치지 않는다.** 지금 호출은 12곳 — 성공 7(관리 6 + `즐겨찾기에 넣었어요`),
  실패 4, 되돌리기 1 — 이라, 기본값을 성공으로 두면 **관리 화면 6곳이 손대지 않고** 정의서대로 `check_circle` 을 얻는다.
- 대신 **실패 4곳**(`FAVORITE_SAVE_FAILED` — 곡 상세 2, 내 악보 2)에 `{ variant: "danger" }` 를 넘긴다. 전부 이번 라운드의 회원 기능 화면이다.
  기본값을 중립으로 두면 반대가 된다 — 관리 화면 6곳을 고치고 회원 화면은 그대로. **고칠 곳이 적은 쪽, 그리고
  고칠 곳이 이번 변경 묶음 안에 있는 쪽**을 고른다.
- `variant` 이름은 `InlineAlert`(`info`/`warning`/`danger`/`success`)에서 그대로 가져온다 — 같은 말을 두 어휘로 쓰지 않는다.
- **중립(`neutral`) 변형은 만들지 않는다.** 아이콘 없는 Toast 는 되돌리기 변형뿐이고, 그건 `action` 이 이미 말한다. 쓰이지 않을 값은 넣지 않는다.

### 29-2. `action`(되돌리기)이 있으면 아이콘은 **그리지 않는다** — `variant` 를 줘도 무시한다

00 §3-11 되돌리기 표의 "아이콘: 없음(중립 알림)" 은 **그 변형의 정의**다. 되돌리기는 성공/실패 판정이 아니라
"방금 한 일을 되돌릴 수 있다" 는 중립 통보이고, 폭 480px 한 줄에 `[아이콘][문구][되돌리기][닫기]` 넷이 서면
문구가 두 줄로 밀린다(같은 절이 곡 제목을 넣지 않기로 한 것과 같은 제약). **닫기는 유지한다**(표에 명시).

| 조합 | 한 줄의 차례 |
|---|---|
| 기본(성공) | `아이콘 → 문구 → 닫기` |
| 실패 | `아이콘(error) → 문구 → 닫기` |
| 되돌리기 | `문구 → 되돌리기 → 닫기` (아이콘 없음) |

### 29-3. 닫기 버튼의 접근 이름은 `알림 닫기` 다

`닫기` 는 곡 상세 라이트박스가 이미 쓴다(`WorkDetailPage.test.jsx` 가 `{ name: "닫기" }` 로 정확히 조회한다).
Toast 는 `document.body` 에 붙고 **화면이 언마운트된 뒤에도 남으므로**(Toast.jsx), 이름이 같으면 다른 화면의 조회가
남아 있는 Toast 를 잡는다. `알림 닫기` 면 정확 일치 조회가 겹치지 않는다.

- 아이콘 `<span class="material-icons" aria-hidden="true">close</span>` + 버튼에 `aria-label="알림 닫기"`.
  material-icons 는 글자(리거처)라 **아이콘마다 `aria-hidden="true"` 가 필수**다 — 안 그러면 낭독에 `check_circle` 이 섞인다.
- **닫기는 되돌리기를 실행하지 않는다.** 닫기 = 그 행동을 그대로 확정한다(새 토스트가 와서 사라질 때와 같다 — 00 §3-11 "겹침").
- 닫으면 자동 사라짐 타이머도 함께 걷는다(`dismissToast` 가 이미 그렇게 한다).

### 29-4. 회귀 위험은 실측으로 확인했다

`role="status"` 를 읽는 기존 테스트 2곳은 **부분 문자열 비교**라 아이콘 글자가 앞에 붙어도 통과한다(§25-1 의 실측 그대로).
`{ name: "닫기" }` 로 버튼을 찾는 테스트는 1곳뿐이고 정확 일치라 `알림 닫기` 와 겹치지 않는다.

- 필요한 클래스: `.toast-icon` · `.toast-message` · `.toast-close`(기존 `.toast-action` 과 나란히), 루트에 `.toast-success` / `.toast-danger`.
  색은 정의서 그대로 — 성공 `--color-success-border`, 실패 `--color-danger-border`.
- 계약 검증: `Toast.variants.test.jsx`(컴포넌트) · `FavoriteToastVariant.test.jsx`(호출부가 변형을 옳게 고르는가).

### 28-5. 테스트에서 10초를 건너뛰는 법 — **가짜 시계는 렌더보다 먼저 깐다** (2026-09-21 senior-dev, 되돌아온 테스트 판정)

이 계약의 Red 3건이 "테스트 결함" 으로 되돌아왔고 **개발자 말이 맞았다.** 원인은 계약이 아니라 **순서**다.

> `vi.useFakeTimers()` 는 **설치 이후에 잡힌 타이머만** 가로챈다. 설치 전에 잡힌 `setTimeout` 은
> `vi.getTimerCount()` 에 보이지도 않고 `advanceTimersByTimeAsync()` 로 발화하지도 않는다(실측).

10초 타이머는 **클릭 시점**에 잡히므로 `클릭 → useFakeTimers()` 순서로 쓴 테스트는 그 타이머를 영영 만나지 못한다.
훅 테스트 4건이 통과한 이유도 같다 — 거기서는 시계를 **렌더 앞**에 깔았다. 규칙은 하나다:

1. **`vi.useFakeTimers()` 는 `render()` 보다 먼저.**
2. 그러면 `waitFor`(=`findText`) 의 폴링·타임아웃 타이머까지 가짜가 돼 영원히 기다린다 —
   RTL 은 vitest 의 가짜 시계를 감지하지 못한다(감지 코드가 `jest` 전역을 본다). 그래서 기다림은
   **직접 시계를 돌려** 만든다: `frontend/src/test/fakeClock.js` 의 `tick(ms)` · `findTextOnFakeClock(text)`.
3. 타이머를 `useEffect` 로 옮겨 피할 수 없다 — passive effect 는 앞선 `act` 안에서 flush 돼 역시 진짜 시계에 잡힌다(실측).

단언은 **약화하지 않고 오히려 조였다**: ⑴ 9.5초까지는 잠긴 채임을 함께 본다(푸는 시점이 정말 10초인가),
⑵ 늦게 온 200 테스트는 응답이 **실제로 도착했는지**(`responded`)와 **날짜 줄이 그대로인지**를 확인하고,
**제때 온 200 은 날짜를 바꾼다**는 대조군을 같은 테스트 안에 둔다 — "안 바뀌었다" 가 공허해지지 않게.
변이 검증(실측): 타이머 제거 → 3건 실패 / `settle` 토큰 검사 제거 → 3건 실패 / 10초를 5초로 → 2건 실패.

### 29-5. 이 구현이 만든 **모양의 부수 효과** 2건 — 둘 다 정의서 쪽이 맞다 (2026-09-21 senior-dev)

| 부수 효과 | 판정 |
|---|---|
| `.toast` 가 flex 한 줄이 되고 닫기(44px 터치 영역) 때문에 **높이가 ~48 → ~68px**. 관리 화면 6곳 토스트도 코드를 안 고쳤는데 커진다 | **받는다.** 00 §3-11 은 `수동 닫기 close` 를 **모든 토스트**에 요구했고, 높이는 그 요구의 산술적 결과다(`--space-3`×2 + `--touch-target`). §29 가 "관리 6곳이 손대지 않고 아이콘을 얻는다" 고 한 것과 같은 성질의 변화다 |
| `.toast-message { flex: 1 }` 이라 되돌리기 변형에서 버튼이 **오른쪽 끝**에 선다(전에는 문구 바로 뒤) | **받는다.** 00 §3-11 되돌리기 표는 "문구 왼쪽 + **오른쪽** 텍스트 버튼 하나" 이고 도해도 오른쪽 끝이다. 전의 모양이 정의서와 달랐던 것 |

**하단 고정 바와의 겹침(designer 제기)** — 토스트는 `bottom: var(--space-6)`(24px)에 뜨고 `--z-toast`(1100)는
`--z-banner`(900) 위다. 그래서 **높이와 무관하게** 바닥에 붙는 바가 있으면 그 위를 덮는다(겹침 조건은 `바 높이 > 24px`).
이번 변경이 만든 위험이 아니다 — 다만 덮는 면적이 44px → 68px 로 늘 뿐이다. 그리고 **지금 저장소에는
바닥 고정 바가 없다**: 스타일시트 전체에서 `bottom:` 오프셋을 쓰는 규칙은 `.toast` **하나뿐**이고,
05·06 의 모바일 sticky 저장바는 아직 정의서에만 있다(실측). 따라서 지금 고칠 것도, 실기기로 확인할 것도 없다.
**그 바를 만드는 라운드**에서 ⑴ 토스트 `bottom` 을 바 높이만큼 올릴지 ⑵ 그 화면에서는 토스트 대신
InlineAlert 를 쓸지를 **그 라운드의 계약으로** 정한다 — 이 항목을 예약해 둔다.

## 30. 추천 근거는 **표 하나**로, 경고 예고는 **전용 읽기 하나**로 (2026-09-21 senior-dev)

기획 `06_추천판본_선정근거와_변경_기획서.md` 를 계약으로 옮기며 내린 구조 결정 셋. 계약 본문은 02 §4-7-2·§5-6-2, 스키마는 01_ERD §3-13.

### 30-1. "고른 이유" 와 "바뀐 이력" 을 두 표로 나누지 않는다

화면은 둘을 다르게 그린다 — 지금 근거는 상자로 크게, 나머지는 접힘 목록. 그래서 "현재 근거 표 + 이력 표" 로 나누고 싶어진다.
**나누지 않는다.** 현재 근거는 **이력의 맨 위 한 줄**이다. 두 표로 두면 지정 한 번에 쓰기가 두 번이고, 언젠가 한쪽만 써지는 날
(예외·부분 실패·다음 사람의 새 경로) 화면이 **어느 쪽을 믿어야 하는지 아무도 답하지 못한다.**
같은 판단을 `download_log`(원장) ↔ `work.download_count`(캐시)에서 이미 한 번 치렀다(01_ERD §3-7 — 실측 13 vs 9).
응답에서 `current` 와 `history[0]` 이 같은 줄인 것은 그래서 **중복이 아니라 같은 객체**다.

### 30-2. 판본 표기를 양쪽 다 스냅샷한다 — "그때 그 값" 이 이 기능의 전부다

기획 §1-3 이 자동 근거에 대해 못 박은 "지정 시점 값으로 박아 둔다" 는 **판본 표기에도 똑같이 적용된다.**
출판사·편집자·연도는 관리자가 고칠 수 있는 값이라, 이력을 그릴 때 살아 있는 판본에서 지금 읽으면
**그때의 판단이 아니라 오늘의 값**이 된다. 게다가 추천 판본을 삭제해 추천이 빠진 곡에서는 그 판본이 아예 없다.
`user_work_download`(§24)가 "삭제된 뒤에도 무엇을 못 주는지 말할 수 있어야 한다" 로 스냅샷을 택한 것과 같은 근거다.

- **`previous` 를 "앞 줄에서 읽기" 로 대신할 수 없다.** 줄이 0개인데 추천은 있는 곡이 실제로 42개다(소급 없음 — 기획 §5).
  그 곡을 처음 다시 지정할 때 "이전 추천" 을 말할 근거가 그 컬럼 말고 없다.
- **양쪽 6필드 대칭**으로 둔다. 화면이 이력 한 줄의 두 판본을 같은 함수로 그리므로, 한쪽만 3필드면
  "왼쪽과 오른쪽이 다른 모양" 이라는 것을 화면이 알아야 하고 designer 가 표기를 한 번 다듬을 때마다 계약이 또 바뀐다.
  컬럼 3개가 그 비용보다 싸다(append-only 라 갱신 경로가 없다).

### 30-3. 경고 6종은 **예고 전용 GET**(§5-6-2)이 계산한다 — 화면이 세지 않는다

경고 ④⑤는 판본의 성질이 아니라 **이 변경의 결과**라, 판정에 곡의 지금 상태(`WorkStatus`)와 다운로드 기록 유무가 필요하다.
화면은 그 둘을 이미 §4-7 로 갖고 있어서 **직접 계산할 수 있다.** 그래도 서버가 한다.

| 안 | 문제 |
|---|---|
| 화면이 계산 | 규칙이 서버(§5-6 응답)와 화면 **두 곳**에 산다. `autoJudgeSkipReason`(§16)에서 이미 "예고와 결과가 어긋나면 안 된다" 로 닫은 문제다. 추천 변경은 사용자가 받는 파일을 바꾸는 동작이라 예고가 틀리면 안 된다 |
| 곡 상세의 판본마다 미리 싣기 | 판본 14개 × 경고 계산을 **매 조회마다**. 게다가 ④⑤는 "그 판본으로 바꿨을 때" 의 가정이라 판본 행의 속성이 아니다 |
| **예고 전용 GET** ✅ | 패널을 열 때 한 번. §5-6 과 **같은 함수**를 쓰므로 예고와 결과가 구조적으로 같다 |

- **§5-6 응답의 `warnings` 도 6종으로 맞춘다.** 필드를 빼면 옛 클라이언트가 조용히 빈 값을 읽고, 기존 회귀 테스트도 뜻을 잃는다.
  다만 **지정 직전 상태로 계산해야 한다** — `WORK_BECOMES_CLOSED` 는 "바꾸면 닫힌다" 는 말이라 지정한 뒤에 세면 **이미 닫혀 있어 영영 뜨지 않는다.** 구현 함정이라 테스트로 잠갔다.
- `RecommendWarning` 에 상수를 **앞쪽에** 더했지만 기존 3종의 상대 순서는 그대로다. `PARTS` 가 `ARRANGEMENT` 앞에 끼어도
  둘은 `kind` 가 하나뿐이라 **동시에 성립할 수 없어** 기존 응답 예시가 한 글자도 바뀌지 않는다(회귀 가드: `RecommendEditionWarningIntegrationTest`).
