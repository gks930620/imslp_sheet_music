# 1. 구분 바 `SectionTabs`

## 레이아웃

**데스크톱 (≥768px)** — 헤더 바로 아래 전폭 띠
```
┌──────────────────────────────────────────────────────────────────────┐
│ [♪ 쉬운악보]  [🔍 곡 이름, 작곡가, 작품번호]  [작곡가] [관리] [👤…]      │  헤더 64px (보라)
├──────────────────────────────────────────────────────────────────────┤
│  피아노    바이올린 [준비 중]   오케스트라 [준비 중]                      │  구분 바 48px (흰 배경)
│  ▔▔▔▔▔▔                                                              │  ← 선택 밑줄 3px primary
├──────────────────────────────────────────────────────────────────────┤   ← 아래 경계선 1px
│ [본문] max-width 1200px …                                             │
```
- 띠 자체는 전폭(`--color-surface`), 안쪽 탭 묶음은 본문과 같은 `--layout-max-width` 로 가운데 정렬해 **좌우 끝이 본문 왼쪽 끝과 맞는다**. 탭은 왼쪽부터 차례로 놓이고 오른쪽 남는 공간은 빈다(균등 분할 아님).

**모바일 (<768px)** — 3등분, 2줄 탭
```
┌────────────────────────────────────┐
│ [♪ 쉬운악보]        [🔍]  [☰]      │  헤더 64px
├────────────────────────────────────┤
│   피아노   │  바이올린  │ 오케스트라 │  구분 바 48px
│           │  준비 중   │  준비 중   │  ← 2줄째, --font-size-xs muted
│  ▔▔▔▔▔▔   │           │           │
├────────────────────────────────────┤
│ [본문]                              │
```
- 폭을 **정확히 3등분**(각 120px @360px). "오케스트라" 5자가 `--font-size-md`(14px)로 70px 이므로 좌우 여백이 남는다. 가로 스크롤 없음, 줄바꿈 없음.
- 준비 중 표시를 라벨 **오른쪽 뱃지**로 두면 360px 에서 넘친다 → 모바일에서만 **아래 줄 작은 글자**로 내린다. 색·모양이 아니라 **글자로** 말하므로 접근성 기준(00 §5)을 지킨다.

## 1-1. 구분 바가 보이는 화면 / 안 보이는 화면

| 보인다 | 안 보인다 |
|---|---|
| 홈, 검색 결과, 곡 상세, 작곡가 목록, 작곡가 상세, **준비 중 안내**, **찾을 수 없는 페이지**(선택 표시 없음 — §3) | 관리 화면 전체(`/admin`, `/admin/**`) — 기획 §3-6. 로그인 화면. 1차 범위 밖이지만 주소가 남아 있는 화면(마이페이지·커뮤니티·채팅) |

- 관리 화면에서 구분 바가 **한 순간도 깜빡이면 안 된다**(인수 조건 8-A 7). 레이아웃 껍데기에서 경로로 판단해 렌더 자체를 하지 않는다.

## 1-2. 왜 "필터 칩"이 아니라 "화면 이동"으로 읽히는가 — 근거 (기획 §3-4)

이 서비스 화면에는 **누르면 목록이 바뀌는 것**(필터 칩)과 **누르면 화면이 바뀌는 것**(구분 탭)이 같은 위쪽 영역에 함께 있다. 둘을 구별하는 신호를 **다섯 겹**으로 준다. 하나만으로는 사용자가 잘못 예측한다.

| # | 신호 | 구분 탭 | 필터 칩 (FilterBar, 00 §3-13) |
|---|---|---|---|
| 1 | **자리** | 헤더에 붙은 **전폭 띠**. 본문 카드 **바깥** | 본문 안, 흰 카드(`.search-filter-section`) **안**, 결과 건수 아래 |
| 2 | **모양** | 밑줄형. 배경 없음, 테두리 없음, 반경 없음 | pill(`--radius-pill`), 배경 채움, 선택 시 primary 배경 |
| 3 | **DOM** | `<a href="/piano">` `<a href="/violin">` `<a href="/orchestra">` — 실제 경로가 붙은 링크. **우클릭 "새 탭에서 열기", 가운데 클릭, 링크 복사가 실제로 동작한다.** 이게 "화면 이동"의 결정적 증거다 | `<button>` — 새 탭이 열리지 않는다 |
| 4 | **접근성 역할** | `<nav aria-label="악기 구분">` + 선택 탭에 `aria-current="page"`. **`role="tab"`/`role="tablist"` 를 쓰지 않는다** — 그 역할은 "같은 화면 안에서 패널만 바꾼다"는 뜻이라 정반대 신호를 준다 | `aria-pressed` 토글 버튼 |
| 5 | **결과** | 주소가 바뀌고 히스토리에 **push** 로 쌓인다. 뒤로 가기로 직전 화면에 돌아온다. 스크롤은 맨 위로 | 주소 쿼리만 갱신, 목록 자리만 다시 그림 |

- **구현 주의(frontend-dev)**: 라우터 링크를 쓰더라도 `href` 속성이 실제로 붙어야 3번 신호가 산다. `onClick` 만 있는 `<div>`/`<span>` 탭은 이 정의서 위반이다.
- 탭 오른쪽에 `chevron_right` 같은 화살표를 **넣지 않는다.** 화살표는 이 서비스에서 "목록 행 → 상세"의 표시다(작곡가 행·작곡가 카드). 탭에 붙이면 세 번째 관습이 생긴다.

## 1-3. 세 가지 "고르는 것"의 시각 대조 (한 화면에 다 나올 수 있다)

검색 결과 화면 위에서 아래로 **구분 탭 → 검색 기준 → 필터 칩** 이 차례로 나온다. 셋이 같아 보이면 화면 전체가 스위치 밭이 된다.

```
┌──────────────────────────────────────────────────────────┐
│  피아노   바이올린 [준비 중]   오케스트라 [준비 중]          │ ① 구분 탭 — 밑줄형, 띠, 링크
│  ▔▔▔▔▔                                                   │    "다른 악보 세계로 간다"
├──────────────────────────────────────────────────────────┤
│  ┌──────┬──────┬────────┐                                │ ② 검색 기준 — 테두리 한 덩어리 안 3칸
│  │ 전체 │ 곡명 │ 작곡가  │   (하나만 선택, 라디오)          │    "검색어를 어느 칸에서 찾나"
│  └──────┴──────┴────────┘                                │
│  ┌────────────────────────────────────┬──────┐           │
│  │🔍 곡 이름, 작곡가, 작품번호로 찾기 …   │ 검색 │           │
│  └────────────────────────────────────┴──────┘           │
│                                                          │
│  '녹턴' 검색 결과 21곡                                     │
│  난이도 (입문)(초급)(중급)(고급)  쪽수 (10쪽 이하)…  ☐ 바로 받기 │ ③ 필터 칩 — pill, 흰 카드 안
│                                                          │    "결과를 줄인다"
└──────────────────────────────────────────────────────────┘
```

| | ① 구분 탭 | ② 검색 기준 | ③ 필터 칩 |
|---|---|---|---|
| 모양 | 밑줄형, 배경 없음 | 한 덩어리 테두리 안 3칸(`--radius-pill` 컨테이너, 칸 사이 1px 구분선) | 낱개 pill |
| 선택 표시 | 3px 밑줄 + primary 글자 | 칸 배경 `--color-primary-light` + 글자 `--color-primary` | 배경 `--color-primary` + 글자 `--color-on-primary` |
| 개수 규칙 | 항상 정확히 1개(404 예외) | 항상 정확히 1개 | 0개 이상, 난이도는 복수 |
| 누르면 | **화면 이동**(push) | 재검색 + 주소 갱신(push, 뒤로 가기로 되돌아감) | 재조회 + 주소 갱신 |
| 자리 | 헤더 아래 띠 | 검색창 바로 위 | 결과 건수 아래 흰 카드 |

- ②와 ③은 둘 다 "결과가 바뀐다"는 점에서 가깝지만, ②는 **항상 하나가 켜져 있고**(빈 상태가 없음) ③은 **전부 꺼진 상태가 기본**이다. 그래서 ②는 라디오 세그먼트, ③은 낱개 토글로 형태를 뗀다.

## 1-4. 준비 중 탭을 왜 비활성(회색·클릭 불가)으로 하지 않는가 — 결정 D2

**결정: 누를 수 있게 한다.** 근거 넷.

1. **비활성이면 안내 화면에 도달할 방법이 사라진다.** 기획 §1-3 은 준비 중 화면을 "빈 목록이 아닌 안내 화면"으로 정의했고, 인수 조건 8-A 4·5·6 이 그 화면 안에서 검증된다. 유일한 입구를 막으면 화면이 죽는다.
2. **`disabled` 는 키보드 포커스를 받지 않고 스크린리더가 건너뛴다.** "앞으로 무엇이 생기는지 알린다"(`00` §12)는 목적 자체가 일부 사용자에게 전달되지 않는다.
3. **"못 누르는 것"은 그 자리에 있을 이유를 설명하지 않는다.** 사용자는 회색 탭을 보고 "언제 열리나? 내가 로그인을 안 해서인가?"를 묻게 되는데, 답할 자리가 없다. 눌러서 열리는 한 문장이 그 답이다.
4. **인수 조건 8-A 2("누르기 전에도 준비 중임이 보인다")는 비활성이 아니어도 지켜진다** — 라벨 옆/아래의 "준비 중" 글자가 그 역할이다. 헛걸음을 막는 것은 비활성이 아니라 **예고**다.

**대신 지켜야 할 것**: 준비 중 탭은 열린 탭보다 **한 단계 조용해야 한다**(글자 `--color-text-muted`). 다만 `--color-text-disabled` 까지 내리지 않는다 — 그 색은 이 서비스에서 "비활성 버튼·미리보기 없음 자리"에만 쓰는 색이라(00 §7 치환표) 누를 수 없다는 뜻이 된다.

## 1-5. 표기 — "피아노"인가 "피아노 독주"인가 (기획 §9 8-2) — 결정 D4

**짧은 이름 "피아노"로 확정.** 근거 셋.

1. **모바일 3등분에서 폭이 결정적이다.** "피아노 독주"(6자)와 "오케스트라"(5자)가 같은 줄에 서면 360px에서 여유가 사라지고, 폰트 폴백에 따라 줄바꿈이 난다.
2. **탭은 사이트 이름 자리이지 설명 자리가 아니다**(기획 §9 8-2 와 같은 판단). 설명은 홈의 한 줄(`한국어로 검색하고 바로 받는 피아노 악보`)이 이미 하고 있다.
3. **나중에 피아노 구분이 네 손 연탄·반주보를 품어도 이름을 다시 바꾸지 않아도 된다.** "피아노 독주"는 지금의 범위를 이름에 못 박는다.

- 화면 어디에도 **"악기 구분"이라는 말 자체를 쓰지 않는다**(기획 §0-1). 라벨은 악기 이름뿐. `aria-label="악기 구분"` 은 화면에 보이지 않으므로 예외.

## 2-1. 이 화면이 "찾을 수 없는 페이지"와 절대 닮으면 안 되는 이유

두 화면 모두 "아이콘 + 제목 + 버튼"이라 시각적으로 가까워지기 쉽다. 다음 세 가지로 뗀다.

| | 준비 중 안내 | 찾을 수 없는 페이지 |
|---|---|---|
| 구분 바 | 그 구분이 **선택돼 있다**(밑줄) | **아무것도 선택돼 있지 않다** |
| 제목의 뜻 | "아직 없다" — **시간**의 문제 | "여기가 아니다" — **주소**의 문제 |
| 아이콘 | `hourglass_empty` (기다림의 아이콘 — 곡 카드 "준비 중" 뱃지와 같은 그림) | `search_off` (실패의 아이콘) |
| 검색창 | 본문에 없음(헤더만) | **본문에 있음**(large, 00 §2-4) |

## 2-2. 왜 본문 검색창이 없는데 헤더 검색창은 살려 두는가

- 본문 검색창은 **"이 화면에서 찾아라"** 는 초대다. 이 구분에는 곡이 하나도 없으므로 그 초대는 반드시 0건으로 끝난다 — 화면이 사용자에게 거짓말을 하는 셈이다.
- 헤더 검색창은 **"여기 말고 다른 데서 찾아라"** 의 자리다(00 §2-1: 홈 이외 모든 화면에 있다). 도착지는 피아노 구분의 결과이고, 도착 화면이 그 사실을 한 줄로 말한다(§2-4). 막다른 화면을 만들지 않는다는 기획 §1-3 의 요구가 이렇게 지켜진다.

## 2-3. 검색어를 들고 왔을 때 (기획 §1-2)

기획 §1-2 는 **"준비 중 구분에 다녀와 돌아오면 검색어·기준·필터·페이지가 그대로 복원된다"** 를 요구한다. 구분 탭이 화면 이동(push)이므로 **브라우저 뒤로 가기**가 그 복원의 기본 수단이다. 다만 모바일 브라우저는 뒤로 가기 버튼이 숨어 있는 경우가 많아, 화면에도 같은 출구를 하나 둔다.

- 형태: **버튼이 아니라 텍스트 링크** (`.btn.btn-text`, 앞에 `chevron_left`). 기획이 정한 "출구 2개"의 시각 위계를 흐리지 않기 위해 세 번째 버튼으로 만들지 않는다.
- 문구: `‹ '녹턴' 검색 결과로 돌아가기` (검색어를 작은따옴표로, 15자 넘으면 앞 15자 + `…`)
- 자리: 출구 버튼 2개 아래 `--space-6` 띄우고 가운데.
- 동작: 직전 검색 결과 화면으로. 검색어·기준·필터·페이지가 그대로.
- **"들고 왔다"의 판정 근거는 주소다** — 준비 중 화면 주소에 `q` 가 있는지로 판단한다(히스토리·referrer 로 판단하지 않는다). 그래야 인수 조건 **8-A 9** 의 세 경우(홈에서 탭 / 곡 상세·작곡가에서 탭 / 검색어 없는 준비 중 주소로 직접 진입)에서 링크가 자동으로 사라지고, **8-A 9 단서**(주소에 검색어가 있어 새로고침·공유 후에도 링크가 보이는 것은 결함이 아니다)와도 맞는다.
- **주소에 담는 것 — 확정(S1·S3 닫힘, API 명세서 §0-5)**: 검색 결과 화면의 쿼리 **`q`·`in`·`level`·`pages`·`downloadable`·`page` 를 이름 그대로** 준비 중 화면 주소에 옮겨 싣는다. **8-B 1** 이 "링크로 돌아오거나 뒤로 가기로 돌아오거나 **두 경로 모두**에서 필터·페이지까지 복원"을 요구하므로 검색어만 담지 않는다.
  - 예: `/piano/search?q=녹턴&in=TITLE&level=ELEMENTARY&page=1` 에서 바이올린 탭 → `/violin?q=녹턴&in=TITLE&level=ELEMENTARY&page=1`. 돌아가기 링크 = `/piano/search?` + **같은 쿼리 그대로**. 기본값 생략 규칙도 같다(`in=ALL` 은 쓰지 않는다).
  - 이 쿼리는 **화면 전용**이다 — 준비 중 화면은 서버 요청을 하지 않으므로 API 로 가는 일이 없다.
  - 홈·곡 상세·작곡가 화면에서 탭을 누르면 쿼리 없이 `/violin` 으로 간다(들고 갈 검색이 없다).
  - `q` 없이 다른 쿼리만 있는 주소(`/violin?page=1`)는 "들고 오지 않은 것"으로 본다 — 링크 없음, 나머지 쿼리는 무시.
- **planner 확인 요청**: 기획 §1-3 문장은 출구를 2개로 적었다. 이 줄은 새 기능이 아니라 §1-2 "복원" 요구를 화면에서 실현하는 수단이라고 판단했다. 불필요하다고 보면 되돌려 달라 — 지우면 복원 수단은 브라우저 뒤로 가기만 남는다.
- IMSLP 출구 문구도 이때 바뀐다: `IMSLP 에서 '녹턴' 찾아보기 ↗`. 검색어가 없으면 `IMSLP 에서 바이올린 악보 직접 찾아보기 ↗`.

## 2-4. 준비 중 화면 → 헤더 검색 → 피아노 결과 (기획 §1-3, 인수 조건 8-A 6)

도착한 검색 결과 화면 **맨 위**(검색창 아래, 작곡가 카드·결과 건수 위)에 한 줄.

```
┌──────────────────────────────────────────────┐
│ ⓘ  바이올린은 준비 중이라 피아노 악보에서 찾았어요.  │   InlineAlert info (00 §3-11)
└──────────────────────────────────────────────┘
```

| 항목 | 값 |
|---|---|
| 컴포넌트 | InlineAlert **info** — `--color-info-bg` / `--color-info` / `--color-info-border`, 아이콘 `info` | 
| 문구 | `{준비 중 구분}은 준비 중이라 피아노 악보에서 찾았어요.` — 조사는 구분마다 고정 문자열로 둔다(`바이올린은` / `오케스트라는`). 프로그램으로 조사를 계산하지 않는다 |
| 언제 보이나 — **확정(S3 닫힘, API 명세서 §0-5)** | 주소에 **화면 전용 쿼리 `from=violin` / `from=orchestra`** 가 있을 때만. 준비 중 화면의 헤더 검색이 `/piano/search?q=…&from=violin` 으로 보낸다. `from=violin` → `바이올린은 …`, `from=orchestra` → `오케스트라는 …`. **API 로 넘기지 않는다** |
| 언제 사라지나 | **이 검색 한 번에만** 보인다. 결과 화면에서 일어나는 **모든 주소 갱신**(재검색·기준 변경·필터 변경·페이지 이동)은 새 주소를 push 하는데, 그때 **`from` 을 이어 붙이지 않는다** → 줄이 사라진다. 화면이 상태를 따로 들지 않는다 — 주소가 유일한 근원 |
| 알 수 없는 값 (`from=cello`, `from=piano`) | 줄을 만들지 않는다. 오류 아님, 나머지 화면은 정상 |
| 새로고침·공유 | 주소에 담겨 있으므로 **유지된다.** 결함이 아니다(8-A 9 단서와 같은 논리) |
| 닫기 버튼 | 두지 않는다(00 §3-11 InlineAlert 규격 그대로) |
| 0건일 때 | 이 줄은 **그대로 보이고**, 그 아래에 0건 화면(§4-7 의 A/B/C 중 하나)이 온다. 이 줄은 0건 안내와 겹치는 말을 하지 않으므로 예외적으로 공존한다 |

# 3. 찾을 수 없는 페이지 — "선택된 구분 없음" 상태 (기획 §6, 인수 조건 8-B 6)

> 기존 정의: `00_공통_레이아웃_토큰.md` §2-4. 여기서 바뀌는 부분만 적는다.

```
┌────────────────────────────────────┐
│ [♪ 쉬운악보]        [🔍]  [☰]      │
├────────────────────────────────────┤
│   피아노   │  바이올린  │ 오케스트라 │  구분 바 — **밑줄 없음. 셋 다 비선택**
│           │  준비 중   │  준비 중   │
├────────────────────────────────────┤
│         [search_off 64px]          │
│      찾을 수 없는 페이지예요           │
│  주소가 틀렸거나, 내려간 곡이거나,     │  ← 보조 문구 교체
│  아직 열지 않은 악기 구분이에요        │
│  [🔍 곡 이름, 작곡가, 작품번호로 찾기] [검색] │
│            [홈으로]                 │
└────────────────────────────────────┘
```

| 항목 | 규칙 |
|---|---|
| 이 화면이 뜨는 주소 | 없는 곡·작곡가 id(기존) + **없는 구분 이름**(`/cello`, `/cello/works/3`) + **준비 중 구분의 하위 경로**(`/violin/search`, `/orchestra/works/3` — 준비 중 구분 아래에는 화면이 없다, API 명세서 §0-5) |
| 구분 바 | 보인다. **어느 탭에도 밑줄·`--color-primary` 글자·`aria-current` 가 없다.** 피아노 탭은 `--color-text-body`, 준비 중 탭은 `--color-text-muted` (평소 비선택 모양 그대로) |
| 보조 문구 | 기존 `주소가 틀렸거나 내려간 곡이에요` → **`주소가 틀렸거나, 내려간 곡이거나, 아직 열지 않은 악기 구분이에요`** (한 문장, `--font-size-md` `--color-text-muted`) |
| 주소의 구분 문자열 | **화면에 되뱉지 않는다.** `'첼로'는 없는 구분이에요` 같은 문구를 만들지 않는다 — 주소에 무엇이 들어올지 알 수 없고(긴 문자열·욕설·깨진 인코딩), 우리는 그것을 그대로 화면에 세울 이유가 없다. 사용자는 자기가 친 주소를 이미 알고 있다 |
| 본문 검색창 | 기존대로 **있다**(large). 이 검색은 **피아노 구분**의 결과 `/piano/search?q=` 로 간다(열린 구분이 하나뿐이므로). §2-4 의 안내 줄은 **띄우지 않는다**(`from` 을 붙이지 않는다) — 사용자가 "구분에서 왔다"고 볼 근거가 없다 |
| "홈으로" 버튼 | 문구 그대로. 피아노 구분 홈 `/piano` 으로 |
| 피아노로 가는 길 | 구분 바의 피아노 탭 + "홈으로" 버튼 **두 개**. 인수 조건 8-B 6 충족 |
| 브라우저 탭 제목 | `찾을 수 없는 페이지 — 쉬운악보` (구분 이름 없음, §5) |

- **곡·작곡가가 없어서 나는 404**(기존 동작)와 **없는 구분 이름 주소로 인한 404** 는 **같은 화면**이다. 화면이 둘을 구별해 다르게 그리지 않는다 — 사용자에게 둘은 같은 사고이고, 구별하려면 위의 "주소 되뱉기"를 해야 한다.

# 4. 검색 기준 선택 `SearchScopeSelect`

## 4-1. 형태

```
데스크톱 (검색창 폭 안, 왼쪽 정렬)
┌──────┬──────┬────────┐
│ 전체 │ 곡명 │ 작곡가  │      높이 40px
└──────┴──────┴────────┘
   ↑ 선택된 칸: 배경 --color-primary-light, 글자 --color-primary, --font-weight-medium

모바일 (폭 100%, 3등분)
┌───────────┬───────────┬───────────┐
│   전체    │   곡명    │   작곡가   │   높이 --touch-target (44px)
└───────────┴───────────┴───────────┘
```

| 항목 | 값 |
|---|---|
| 컨테이너 | `1px solid --color-border`, `--radius-pill`, 배경 `--color-surface`, `overflow: hidden` |
| 칸 | 데스크톱 padding `0 --space-4` 높이 40px / 모바일 폭 1fr 높이 `--touch-target`. 칸 사이 `1px solid --color-border` |
| 글자 | `--font-size-md`. 비선택 `--color-text-secondary`, 선택 `--color-primary` `--font-weight-medium` |
| 선택 칸 배경 | `--color-primary-light` |
| hover(비선택) | 배경 `--color-surface-muted` |
| 포커스 | 00 §5 포커스 링 규칙(`:focus-visible` outline 2px `--color-primary`, offset 2px). 컨테이너가 `overflow:hidden` 이라 outline 이 잘리지 않도록 offset 을 **안쪽(-2px)** 으로 준다 |
| 마크업 | **라디오 그룹** — `role="radiogroup"` + `aria-label="검색 기준"`, 각 칸은 `<button role="radio" aria-checked>` 또는 시각 숨김 `<input type=radio>` + `<label>`. **`<select>` 드롭다운을 쓰지 않는다**(§4-2) |
| 키보드 | Tab 으로 그룹에 진입 → **좌우 화살표로 칸 이동**(라디오 그룹의 표준 동작). 이동 즉시 선택된다 |
| 라벨 텍스트 | 화면에 `찾을 곳:` 같은 라벨을 **붙이지 않는다.** 좁은 폭에서 입력 폭을 뺏고, 세 칸의 내용("전체·곡명·작곡가")이 이미 무엇을 고르는지 말한다. 대신 `aria-label` 로 보완 |
| **주소** — 확정(S1 닫힘) | 쿼리 이름 **`in`**, 값 `TITLE` / `COMPOSER`(**대문자**로 쓴다 — 계약 §3-1 의 enum 과 같은 표기로 통일, 서버는 대소문자 무시 — API 명세서 §3-1). **"전체"는 주소에 `in` 을 쓰지 않는다**(기본값 생략, §0-5) → `/piano/search?q=월광` 이 기준 없던 시절 주소와 같은 모양이고 옛 링크가 그대로 열린다(인수 조건 8-F 3). 칸을 누르면 `in` 을 바꾼 새 주소를 push, "전체"를 누르면 `in` 을 뗀다 |

## 4-2. 왜 검색창 "위"인가 — 결정 D6 근거

세 가지 안을 놓고 정했다.

| 안 | 장점 | 왜 탈락 / 채택 |
|---|---|---|
| (a) 검색창 **왼쪽 안쪽**에 붙인 드롭다운 (쇼핑몰 카테고리 검색 방식) | 검색창과 한 몸으로 보인다 | **탈락.** 360px 에서 입력칸 폭을 80~90px 뺏는다. 이 서비스의 자리 문구는 `곡 이름, 작곡가, 작품번호로 찾기 — 예: …` 로 길고, 00 §6 은 **360px에서 자리 문구가 잘리지 않을 것**을 못 박았다. 자리 문구가 잘리면 "무엇을 칠 수 있는지"라는 더 큰 정보가 죽는다 |
| (b) 검색창 **바로 위** 세그먼트 3칸 | 입력 폭을 하나도 뺏지 않는다. 세 선택지가 **항상 다 보여** 누르기 전에 발견된다. 읽는 순서가 "어디에서 → 무엇을"이 된다 | **채택** |
| (c) 검색창 **아래** | 위 공간을 아낀다 | **탈락.** 결과 화면에서 필터 바와 같은 방향(아래)에 놓여 "필터의 일종"으로 읽힌다(§1-3). 그리고 사용자가 이미 다 치고 Enter 를 누른 **뒤에야** 발견하게 된다 |

- **드롭다운(`<select>`)을 쓰지 않는 이유**: 선택지가 3개뿐인데 드롭다운은 ① 접혀 있어 발견되지 않고 ② 고르는 데 탭이 두 번 들며 ③ 모바일에서 OS 기본 피커가 화면 절반을 덮는다. 사용자 요청의 "select 로 고르게"는 **하나만 고르게 하라**는 뜻이지 드롭다운 위젯을 지정한 것으로 읽지 않았다 — 세그먼트가 같은 요구를 더 잘 만족한다. *(다르게 보면 되돌려 달라 — §7)*
- **세로 위치 관계**: 세그먼트와 검색창 사이 `--space-2`(8px), 세그먼트 위 `--space-4`. 세그먼트의 **왼쪽 끝을 검색창 왼쪽 끝에 맞춘다** — 두 요소가 한 덩어리로 읽히는 핵심이다.
- **홈에서는 검색창이 가운데 정렬**(최대 720px)이므로 세그먼트도 그 720px 묶음의 **왼쪽 끝에 맞춰** 왼쪽 정렬한다(가운데 정렬하지 않는다). 검색창과 왼쪽 끝이 어긋나면 별개 요소로 보인다.

## 4-3. 기준별 자리 문구(placeholder) — 결정

기획 §4-5 초안을 다듬고, 00 §3-1 의 **360px 대응 짧은 버전** 규칙을 세 기준 모두에 적용한다.

| 기준 | large 자리 문구 (데스크톱·일반) | 짧은 버전 (360px에서 잘릴 때) |
|---|---|---|
| **전체** | `곡 이름, 작곡가, 작품번호로 찾기 — 예: 월광, 쇼팽 녹턴, K.545` *(기존 그대로)* | `곡 이름, 작곡가, 작품번호 — 예: 월광, K.545` *(기존 그대로)* |
| **곡명** | `곡 이름으로 찾기 — 예: 월광, 엘리제를 위하여, Op.27 No.2` | `곡 이름 — 예: 월광, Op.27 No.2` |
| **작곡가** | `작곡가 이름으로 찾기 — 예: 쇼팽, 베토벤, Chopin` | `작곡가 이름 — 예: 쇼팽, 베토벤` |

- **곡명의 예시에 `Op.27 No.2` 를 반드시 남긴다.** 작품번호가 곡명에 포함된다는 기획 §4-2 의 결정을 사용자에게 알릴 유일한 자리다. 이게 없으면 사용자는 작품번호를 칠 때 기준을 "전체"로 되돌려야 한다고 오해한다.
- **작곡가의 예시에 원어(`Chopin`)를 남긴다.** 원어 표기로도 찾아진다는 사실을 말하는 자리다.
- 헤더 검색창(compact)의 자리 문구는 **바뀌지 않는다** — 헤더는 항상 "전체"이므로 `곡 이름, 작곡가, 작품번호` 가 맞다 (기획 §7 충돌 7).
- 기준을 바꾸면 자리 문구도 **즉시** 바뀐다. 입력칸에 이미 친 글자는 **지우지 않는다**.

## 4-4. 기준을 바꿀 때 화면에서 일어나는 일 (기획 §4-3)

| 상황 | 화면 |
|---|---|
| 결과 화면 + 검색어 있음 | 누른 칸이 즉시 선택 표시 → 목록 자리만 스켈레톤 → 새 결과. **검색창·세그먼트·필터 바는 다시 그리지 않는다**(자리가 튀지 않게). 스크롤 위치 유지, 페이지는 1페이지 |
| 결과 화면 + 필터 걸려 있음 | 필터 칩 선택 상태 **그대로 유지**(구분 전환과 다르다). 필터 바가 깜빡이지 않는다 |
| 홈 + 검색어 아직 안 침 | 선택 표시와 자리 문구만 바뀐다. **화면 이동 없음, 예시 칩만 교체**(§4-5) |
| 결과 화면 + 검색창이 빈 상태 | **아무 일도 일어나지 않는다.** 이동 없음, 오류 문구 없음, 흔들림 없음. 선택 표시만 바뀐다 (인수 조건 8-E 2) |
| 뒤로 가기 | 바꾸기 전 기준의 결과로 돌아가고 **세그먼트 선택 표시도 함께 되돌아간다** (주소가 유일한 근원) |
| 주소의 기준 값이 이상함 (`in=xyz`, `in=`) | **"전체"가 선택돼 보인다.** 오류 화면·경고 문구 없음 (인수 조건 8-F 4). **확정(S4 닫힘)**: 서버가 알 수 없는 `in` 을 `ALL` 로 열어 **200** 을 주고, 응답의 `in` 은 관용 처리가 끝난 확정값(`"ALL"`)이다 — 세그먼트는 **응답의 `in`** 으로 그린다(API 명세서 §3-1). 응답 전에는 주소 값을 같은 규칙(대소문자 무시, 셋 밖이면 전체)으로 읽으므로 두 값이 늘 같다. *(구분 `section` 은 반대로 400 — "어느 세계인가"라 조용히 다른 세계를 보여주면 안 된다. 그러나 없는 구분 이름은 라우터가 먼저 404 화면으로 보내므로 이 요청은 API 까지 가지 않는다, §3)* |

## 4-5. 홈 예시 칩은 기준을 따라 바뀐다 — 결정 D9

`01_홈` 의 예시 칩(`예: 월광 · 쇼팽 녹턴 · K.545`)을 그대로 두면, 기준이 "곡명"일 때 **작곡가 이름이 든 칩(`쇼팽 녹턴`)이 곡명 칩에 남는다.** 시드에서는 별칭 `쇼팽 녹턴` 이 곡명 칸에 있어 이 칩이 곡명으로도 2곡을 내지만(0건이 아니고 결함도 아니다), 그건 **별칭 큐레이션에 기댄 우연**이다 — 별칭에 작곡가 이름이 없는 곡에서는 확실히 0건이 된다(예: `베토벤 엘리제` → 곡명 0건. 기획 `04` §4-2-1·§4-6 1). 우리가 보여준 칩이 0건으로 가는 일이 없도록 **곡명 칩은 곡 이름·작품번호로만** 짠다. 화면이 스스로 팔 수 있는 함정은 화면이 미리 메운다.

| 기준 | 예시 칩 3개 |
|---|---|
| 전체 | `월광` `쇼팽 녹턴` `K.545` *(기존 그대로)* |
| 곡명 | `월광` `엘리제를 위하여` `Op.27 No.2` |
| 작곡가 | `쇼팽` `베토벤` `모차르트` |

- 칩을 누르면 **현재 선택된 기준 그대로** 검색한다(칩이 기준을 바꾸지 않는다).
- 칩 3개는 고정이고 서버에서 받아오지 않는다(기존 규칙 유지).

## 4-6. 헤더 검색창에 기준 선택을 두지 않는다 — 결정 D7 (기획 §9 8-9 에 대한 답)

**기획의 결정에 동의한다. 되돌리지 않는다.** designer 가 더하는 근거:

1. **자리가 물리적으로 없다.** 헤더 검색창은 compact(높이 40px)이고, 모바일에서는 🔍 토글로 펼쳐지는 **한 줄**이다. 여기에 3칸 세그먼트를 넣으면 360px에서 입력 폭이 절반이 되거나 헤더가 두 줄이 된다 — 헤더 높이 `--header-height`(64px)는 전 화면의 sticky 계산에 쓰이는 값이라 함부로 못 늘린다.
2. **헤더 검색은 "이 화면을 떠나는 도구"** 다. 목적지(검색 결과)에 선택 자리가 있으므로 기준은 도착해서 바꾸면 된다 — 두 번 물을 필요가 없다.
3. **가장 큰 위험은 "작곡가"인 채로 곡 이름을 치는 사고**인데, 헤더에 선택이 없으면 그 사고가 구조적으로 일어나지 않는다.

## 4-7. 0건 화면의 줄 순서 — 결정 D8 (기획 §4-4)

**원칙: 한 화면에 빈 상태 블록은 하나뿐이다.** 세 경우는 상호 배타이며 **절대 쌓이지 않는다.** 여러 안내가 동시에 뜨면 사용자는 무엇도 읽지 않는다.

```
결과 0건
  │
  ├─ 필터가 하나라도 선택돼 있나? ──── 예 ──▶ [A] 필터 안내만
  │                                          (기준 이야기 없음, 인기곡 없음
  │                                           + 작곡가 카드 1명이면 딸린 출구 한 줄)
  └─ 아니오
       │
       ├─ 기준이 "곡명"/"작곡가"이고, 전체 기준에 결과가 있다고 확인됨? ─ 예 ─▶ [B] "전체로 찾기" 하나
       │                                                                    (기존 3줄·인기곡 없음)
       └─ 그 외(기준=전체이거나, 전체로도 0건이거나, 알 수 없음) ────────▶ [C] 기존 0건 안내
```

### [A] 필터 때문에 0건
- 필터 바 **유지**(선택 상태가 보여야 원인이 보인다). 목록 자리에 `.empty-state` `filter_alt_off` + 제목 `이 조건에 맞는 곡이 없어요` + `.btn.btn-secondary` `필터 해제`.
- **기준 관련 안내·기존 0건 3줄·인기곡·작곡가 목록 링크가 하나도 나오지 않는다.**
- **단 하나의 예외**: 작곡가 일치 카드가 **정확히 1명** 떠 있으면 `필터 해제` 버튼 아래에 텍스트 링크 한 줄 — `쇼팽의 곡은 10개 등록돼 있어요 — 조건 없이 모두 보기 →` (기획 `01` §5·§11-4, 인수 조건 `01` §6). 이 줄은 **0건 안내가 아니라 카드에 딸린 출구**이고 조언이 아니라 확실한 클릭이라 위 금지 목록에 걸리지 않는다. 규격·근거·"카드가 2명 이상이면 붙이지 않는다"는 **`02_검색결과.md` "[A] 안에서 유일하게 허용되는 한 줄"** 이 단일 기준이다.
- 화면은 "필터를 다 풀면 결과가 있는가"를 알 필요가 없다. **필터가 선택돼 있으면 무조건 A** 다. 필터를 풀었는데도 0건이면 그때 화면이 B 또는 C 로 넘어간다 — 기획 §4-4 의 "가까운 원인부터 말한다"가 이 2단계로 그대로 실현된다.

### [B] 기준이 전체가 아니고, 전체 기준에 결과가 있을 때
```
┌──────────────────────────────────────────────┐
│              [search_off 64px]               │
│                                              │
│   'Chopin 녹턴'을 곡명에서 찾지 못했어요          │  ← 제목: 원인
│                                              │
│   전체에서 찾으면 2곡이 있어요                   │  ← 보조: 사실 (시드 실제값)
│                                              │
│        ┌──────────────────────┐              │
│        │   전체로 찾기  →      │              │  ← .btn.btn-primary
│        └──────────────────────┘              │
└──────────────────────────────────────────────┘
```
| 항목 | 값 |
|---|---|
| 제목 | `'{검색어}'은(는) {기준}에서 찾지 못했어요` — 조사 계산을 피해 **두 벌 고정 문구**로 둔다: 곡명 `'{검색어}'을 곡명에서 찾지 못했어요` / 작곡가 `'{검색어}'을 작곡가 이름에서 찾지 못했어요`. 검색어 부분 `--color-primary`. `--font-size-lg` |
| 보조 | `전체에서 찾으면 {N}곡이 있어요` (`--font-size-md` `--color-text-muted`). `{N}` 은 응답 `totalInAll`. 건수 표기는 00 §4 규칙. 시안의 `2곡` 은 시드 실제값 — `Chopin 녹턴` 전체 기준 = 녹턴 Op.9·녹턴 20번(기획 `04` §4-2-1) |
| 버튼 | `전체로 찾기` + `arrow_forward`. `.btn.btn-primary`. 누르면 기준이 "전체"로 바뀌고 같은 검색어로 재검색(주소 갱신, push) |
| **여기 없는 것** | 기존 0건 3줄, 인기곡 5개, 작곡가 목록 보기 버튼, IMSLP 링크. **전부 숨긴다** |
| 왜 다 숨기나 | 지금 사용자에게 필요한 건 **클릭 하나**다. 전체 결과가 확실히 있는 상태(시드의 `Chopin 녹턴` 이면 2곡)에서 "다른 이름으로 불리기도 해요" 같은 조언을 함께 주면, 확실한 출구가 조언 더미에 묻힌다. 다른 출구도 이미 화면에 있다 — 위의 기준 세그먼트("전체" 칸)와 검색창 |

- **시안 검색어가 `Chopin 녹턴` 인 이유(2026-09-10 교체, 2026-09-11 planner 확정 — 기획 `04` 개정 6 §4-2-1)**: 처음 시안은 `쇼팽 녹턴` 이었으나, 시드의 쇼팽 곡 10곡이 전부 `쇼팽 녹턴` 같은 **한글 작곡가 이름이 든 별칭**을 갖고 있어 곡명 기준에서도 걸린다(`쇼팽 녹턴` → 곡명으로도 **2곡**. 0건이면 그때가 결함). `Chopin` 은 작곡가 **원어 표기**라 50곡 어느 곡명 칸(제목·원어·작품번호·별칭)에도 없고 작곡가 칸에만 있다 → **곡명 0건 · 전체 2곡(녹턴 Op.9·녹턴 20번)** 이 시드에서 실제로 성립한다. 시안의 숫자 `2곡` 은 예시가 아니라 **시드 실제값**이다 — qa 는 이 화면을 `Chopin 녹턴` 으로 재현하고 숫자까지 대조한다(다른 재현 검색어: `베토벤 엘리제`·`모차르트 작은별`·`멘델스존`, 각 0건 → 1곡). 별칭은 관리자가 고칠 수 있으므로 운영 데이터에서는 숫자가 달라질 수 있다.

### [B] 판정 정보 — **확정(S2 닫힘): 검색 응답의 `totalInAll`** (API 명세서 §3-1)

기획 §4-4 가 못 박은 것: **"전체 기준으로 결과가 실제로 있을 때만 이 줄이 뜬다."** 검색 응답의 `totalInAll` 이 그 판정값이다 — **같은 구분 · 같은 검색어 · 기준 전체 · 필터 없음**의 곡 수.

| 응답 `totalInAll` | 언제 | 화면 |
|---|---|---|
| **정수 N > 0** | 기준이 곡명/작곡가 | **[B]** — `전체에서 찾으면 N곡이 있어요` |
| **`0`** | 기준이 곡명/작곡가, 전체로도 0건 | **[C]** — 사실 고지 줄(`지금은 '곡명'에서만 찾고 있어요`) 표시 |
| **`null`** (모름) | 기준이 전체일 때만 — 질문 자체가 성립하지 않는다 | **[C]** — [B] 검사를 하지 않는다. 사실 고지 줄도 없다(기준=전체) |

- **화면은 "모름"(`null`)과 "0건"(`0`)을 절대 같게 취급하지 않는다.** 계약이 셋(숫자 / 0 / null)을 구분해 주므로 화면이 [B] 를 추측으로 띄우는 경우가 없다. **frontend-dev 주의**: `!totalInAll` 같은 판정은 `0` 과 `null` 을 뭉갠다 — `totalInAll != null && totalInAll > 0` 처럼 셋을 갈라 읽는다.
- 이전 시안의 "있다/없다만 아는 경우"(숫자 없는 `전체에서 찾으면 결과가 있어요`)는 **쓰지 않는다** — 계약이 항상 정수를 준다.
- 숫자가 **필터 없이** 센 값인 것과 화면이 맞는다: [B] 는 [A](필터 있음)를 지나 필터가 없는 상태에서만 나온다.

# 5. 브라우저 탭 제목 (기획 §3-7, §9 8-4) — 결정 D5

**넣는다. 형식: `{화면 고유 부분} — 쉬운악보 {구분}`**

| 화면 | `<title>` |
|---|---|
| 피아노 홈 | `쉬운악보 — 피아노` |
| 검색 결과 | `'녹턴' 검색 결과 — 쉬운악보 피아노` |
| 곡 상세 | `월광 소나타 — 쉬운악보 피아노` |
| 작곡가 목록 | `작곡가 — 쉬운악보 피아노` |
| 작곡가 상세 | `쇼팽 — 쉬운악보 피아노` |
| 준비 중 안내 | `바이올린 준비 중 — 쉬운악보` |
| 찾을 수 없음 | `찾을 수 없는 페이지 — 쉬운악보` |
| 관리 화면 | `관리 — 쉬운악보` (구분 없음) |
| 로그인 | `로그인 — 쉬운악보` |

- 규칙: **구분이 걸리는 화면에만** 뒤에 구분 이름이 붙는다. 준비 중·404·관리·로그인에는 붙지 않는다(그 화면은 어느 구분의 "안"이 아니다).
- **푸터에는 구분을 넣지 않는다.** 푸터 3줄(00 §2-2)은 출처·저작권 고지 자리다. 구분 이름을 넣으면 "고지 내용이 구분마다 다른가?"라는 없는 질문을 만든다. 상단 탭과 탭 제목이 이미 두 번 말하고 있다.
- `index.html` 의 기본 `<title>` 은 `쉬운악보` 그대로 두고, 화면마다 갱신한다. **갱신 수단 확정(S5 닫힘, `03_기술결정.md` §21-7)**: 라이브러리 없이 **`useDocumentTitle(title)` 훅** 하나(`document.title` 대입, 언마운트 시 기본값 복귀 없음 — 다음 화면이 곧바로 자기 제목을 쓴다). 화면 컴포넌트가 이 표의 문자열로 호출한다. 곡 상세가 응답 `section` 으로 자기 교정(`03` 상태표)한 뒤에는 그 구분 이름으로 제목을 쓴다.

# 6. 토큰 — 추가한 것과 추가하지 않은 것

## 추가 (1개)

```css
--section-tabs-height: 48px;   /* 헤더 아래 악기 구분 바 (모바일 2줄 / 데스크톱 1줄 공통) */
```
- 헤더(`--header-height`)와 같은 성격의 **전역 구조물 높이**라 이름이 필요하다. 모바일 2줄 배치가 48px 을 요구하고, 데스크톱도 같은 값으로 통일해 **미디어 쿼리 안에서 변수를 재정의하지 않아도 되게** 했다(tokens.css 를 단순하게 유지).

## 추가하지 않은 것 (기존 토큰으로 해결)

| 필요했던 것 | 쓴 기존 토큰 |
|---|---|
| 준비 중 뱃지 색 | `--badge-preparing-bg` / `-text` (곡 카드 "준비 중" 뱃지와 **같은 색으로 묶는 게 오히려 이득**) |
| 구분 바 배경·경계 | `--color-surface`, `--color-border` |
| 선택 밑줄 색 | `--color-primary` (두께 3px 은 컴포넌트 고유 값 — 토큰화하지 않는다) |
| 기준 세그먼트 선택 배경·글자 | `--color-primary-light`, `--color-primary` |
| 세그먼트 모바일 높이 | `--touch-target` |
| 준비 중 화면 아이콘 크기 | `--icon-size-empty` |
| 준비 중 화면 본문 폭 | `--layout-narrow-width` |
| 안내 줄(피아노에서 찾았어요) | `--color-info-*` (InlineAlert info) |

## 구분 바를 sticky 로 만들지 않는 이유 — 결정 D3

1. **탭은 표지판이지 도구가 아니다.** 구분 전환은 한 방문에 많아야 두세 번이다. 스크롤 내내 자리를 차지할 이유가 없다.
2. **모바일 세로 공간.** 헤더 64 + 탭 48 = 112px 이 상시 점유되면 360×640 화면의 17%가 사라진다. 이 서비스의 본문은 곡 목록이라 세로가 곧 정보량이다.
3. **기존 sticky 와 충돌하지 않는다.** `04_작곡가` 의 가나다 구분 헤더가 `top: var(--header-height)` 로 붙어 있다. 구분 바가 sticky 가 되면 이 값이 `calc(--header-height + --section-tabs-height)` 로 바뀌어야 하고, 앞으로 sticky 를 쓰는 모든 화면이 같은 계산을 안고 간다.
4. "지금 어느 구분인가"(기획 §1-4)는 **주소·탭 제목·화면 상단** 세 곳이 답한다. 스크롤을 맨 위로 올리면 탭이 바로 보인다.
