# 하네스 오케스트레이션 가이드

메인 세션(지휘자)이 서브에이전트를 어떻게 부리는지에 대한 규칙이다.
핵심은 **"AI 한 명한테 다 시키지 않는다"** — 일을 쪼개서 역할별로 넘긴다.

## 언제 팀을 쓰나 (판단 기준)

| 상황 | 처리 |
|---|---|
| 한두 줄 수정, 단순 질문 | **팀 안 씀.** 메인 세션이 그냥 처리 |
| 여러 파일·여러 단계가 걸린 기능 | **풀 파이프라인** (기획→구현→검토) |
| "이거 어디 있지?" 류 탐색 | **researcher만** 호출 |
| 이미 계획이 명확함 | planner 건너뛰고 **builder부터** |
| 구현 끝, 품질만 확인 | **reviewer만** 호출 |

> 과하게 쓰지 마라. 팀을 나누는 건 공짜가 아니다(컨텍스트·시간). **복잡할 때만** 나눈다.

## 기본 흐름 (풀 파이프라인)

1. **(선택) researcher** — 모르는 사실이 있으면 먼저 조사시킨다.
   → 반환된 "사실 요약"을 다음 단계에 넘긴다.

2. **planner** — 요구사항 + 조사 결과를 주고 계획을 받는다.
   → 반환된 "계획"을 사람에게 한 번 보여주고, 애매하면 확인받는다.

3. **builder** — 승인된 계획을 그대로 주고 구현시킨다.
   → 반환된 "변경 사항 + 확인 결과"를 받는다.

4. **reviewer** — builder의 변경을 주고 점검시킨다.
   → **통과**면 끝. **수정 필요**면 그 지적을 다시 **builder에게** 넘겨 고친다(=verify 루프).

```
researcher → planner → builder → reviewer ──통과──▶ 완료
                          ▲                │
                          └──수정 필요──────┘
```

## 에이전트 간 데이터 전달 규칙

서브에이전트는 **격리된 컨텍스트**에서 돈다. 내가 준 것만 보고, 요약만 돌려준다. 그래서:

- **넘길 때**: 다음 에이전트가 알아야 할 것을 명시적으로 다 적어준다. "아까 그거" 식으로 말하지 않는다.
  - planner에게 → 요구사항 원문 + 조사 결과
  - builder에게 → 계획 전문 + 관련 파일 경로
  - reviewer에게 → 무엇이 바뀌었는지(파일 목록) + 원래 요구사항
- **받을 때**: 각 에이전트의 "반환 형식"대로 온다. 그걸 그대로 다음 단계 입력으로 쓴다.

## 실패·되돌림 처리

- reviewer가 "수정 필요"를 3번 넘게 반복하면 → 멈추고 사람에게 상황을 보고한다. (무한 루프 방지)
- 에이전트가 계획을 벗어나거나 막히면 → 억지로 진행하지 말고 사람에게 결정을 넘긴다.
- builder가 "테스트 깨짐"을 보고하면 → 감추지 말고 그대로 사람에게 전달한다.

## 호출 예시 (사람이 메인 세션에 하는 말)

- `"이 기능 하네스로 처리해줘"` → 풀 파이프라인 가동
- `"researcher로 이거 먼저 조사해줘"` → 조사만
- `"reviewer로 방금 변경 점검해줘"` → 검토만
